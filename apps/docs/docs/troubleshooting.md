---
title: Troubleshooting
---

Find the symptom, then apply the fix. Each cookbook lists only the problems that are specific to its steps; everything else is collected here.

When a wallet is involved, collect its log right after the failure: in the EU Reference Implementation open **Settings → Retrieve Logs**, in Paradym Wallet open **Settings → Export Logs**. The [wallet compatibility record](reference/wallet-compatibility.md) has details for other wallets. On the EUDIPLO side, open the session under **Sessions → All Sessions** in the Web Client: a failed session shows why it failed, its failure code where one is recorded, and the wallet's own description when the wallet reported the failure. `GET /api/session/{id}` returns the same as described in [Session Outcome](reference/session-outcome.md). Remove tokens, keys and personal data before you share logs.

## Install and connect

| Symptom                                                   | Cause                                                                       | Fix                                                                                                                                                       |
| --------------------------------------------------------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `eudiplo: command not found` after the installer ran      | `~/.local/bin` is not on your `PATH`                                        | Add `export PATH="$HOME/.local/bin:$PATH"` to your shell profile and open a new shell.                                                                   |
| Installer stops with "npm is required"                    | No standalone build for this platform (for example an Intel Mac); the installer falls back to npm | Install Node.js 22.12 or later, then rerun the installer, or use `npx @eudiplo/cli`.                                                                   |
| `Docker or Podman was not found`                          | No container runtime on the `PATH`, or it is not running                    | Install and start Docker or Podman; set `EUDIPLO_CONTAINER_RUNTIME=docker` or `podman` to choose one.                                                    |
| "port is already allocated" when starting                 | Another EUDIPLO stack, often `eudiplo demo`, uses port `3000` or `4200`     | Stop it, for example `eudiplo down --instance local` for the demo, then run `eudiplo up --instance <name>`.                                              |
| `Unknown instance` or a command acts on the wrong stack   | The CLI default instance is a different one                                 | Run `eudiplo instance list` and pass `--instance <name>`, or make it the default with `eudiplo instance use <name>`.                                     |
| An edit to `.eudiplo.env` has no effect                   | The running container still has the old environment                         | Run `eudiplo up --instance <name>`; Compose recreates changed containers. `eudiplo restart` does not reload the environment.                              |
| Backend exits right after start                           | Invalid environment, for example a malformed `CORS_ORIGINS` or a missing secret | Read `eudiplo logs --instance <name> --service eudiplo --tail 100`; the first error names the variable.                                              |
| `localhost` health works, the phone cannot reach the backend | The tunnel stopped, forwards to another port, or shows a confirmation page | Restart the tunnel to port `3000`. Open `https://<public-host>/health` in the phone's browser; it must show the JSON directly.                          |

## Login

| Symptom                                                   | Cause                                                                       | Fix                                                                                                                                                       |
| --------------------------------------------------------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Web Client login hangs or reports a connection error      | **EUDIPLO Instance** points to an address the browser cannot reach, such as `http://eudiplo:3000`, which older Compose files prefill | Enter the backend address as your browser reaches it, for example `http://localhost:3000`. A trailing slash is removed automatically.  |
| Web Client login hangs or reports a connection error, although `<EUDIPLO Instance>/health` opens in the browser | The token request fails. It goes to the token endpoint of the discovery document, `PUBLIC_URL/api/oauth2/token` (with `OIDC` set, the provider's), not to the **EUDIPLO Instance**: for example a stopped tunnel, a WAF or proxy that blocks the browser's address, or a CORS error | Open `PUBLIC_URL/health` (with `OIDC`, the provider's address) in the same browser and start the tunnel or proxy, or correct `PUBLIC_URL` and run `eudiplo up`. The browser's network tab shows the failing request ([web client addresses](operate/docker-compose.md#web-client-addresses)). |
| Login page shows "Resuming the session of …" instead of the form | The open tab kept its session and keeps renewing its token, but the token request gets no answer (backend stopped, restarting or removed), fails with an error other than `400` or `401`, or is blocked for CORS | Open `<backend>/health` in the browser, at `PUBLIC_URL` if it differs from the **EUDIPLO Instance** (the token endpoint is there, see the row above). If it does not answer, start the backend; the page then signs in by itself and returns to the page you were on. For a CORS error in the browser console, see the CORS row below. To sign in elsewhere, choose **Sign out and use other credentials**; you need the client secret again. |
| "Your session expires in … minutes", "Your session has expired" or, on the login page, "The session of … expired" some time after a page reload or in a newly opened tab | The Web Client keeps the client secret in memory only, in the tab you logged in with. Only that tab renews the token; a reloaded tab, or one opened later, takes over each token it renews. Once no open tab holds the secret, for example because that tab was closed or reloaded too, the session lasts until the token expires ([token lifetime](reference/api.md#authentication)) | Keep the tab you logged in with open, or log in again. The login form keeps the client ID and instance, so enter the client secret; signing in as the same client returns to the page you were on. |
| Login rejected with valid-looking credentials             | Wrong client ID or secret                                                   | `eudiplo demo` uses `root` / `root`; `eudiplo init` generates the secret, see `AUTH_CLIENT_SECRET` in `.eudiplo.env`. Tenant clients: rotate the secret under **Administration → API Clients**. |
| The token endpoint always answers `401`                   | The instance uses an external OIDC provider such as Keycloak                | Use the **SSO** tab, or get tokens from the identity provider. See [Keycloak SSO](operate/keycloak.md).                                                  |
| "Your API client no longer has access"                     | The client you signed in with was deleted, or its tenant was, or its secret changed | Sign in with another client, or with the new secret. To give a service access again, create its client again or give it the new secret ([revoke access](operate/tenants-and-access.md#revoke-access)). |
| "Your API client no longer has the role …"                 | Someone removed a role from the client you signed in with | The Web Client hides the pages of that role. On a page that needs it, copy unsaved changes and choose **Leave page**. Ask for the role again if you need it. |
| "Your API client may have lost a role this page needs" in a reloaded tab, or one opened later | The backend refused a request of the page for missing roles. Without the client secret, the tab cannot get a new token to check which roles the client has now, and its menu still shows the pages of the token's roles | Choose **Log in** and sign in again; the new token carries the client's current roles. Copy unsaved changes first. |
| Signed in, but menu sections are missing                  | The client lacks the roles for them                                         | Have a client that holds the roles, or `tenant:admin`, add them; without `tenant:admin`, a client cannot add roles to itself ([granting roles](reference/roles.md#granting-roles)). Then sign in again: the Web Client builds its menu from the roles in its token. |
| API calls return `401` with "The client of this token does not exist" or "This token was issued for the client's earlier credentials" | The client was deleted, its tenant was, or it got a new secret (also by a configuration import) since the token was issued | Request a new token with the current secret. To give a service access again, create its client again or give it the new secret ([revoke access](operate/tenants-and-access.md#revoke-access)). |
| API calls return `403`                                    | The client lacks the role of the endpoint, for example `issuance:offer` (with Keycloak: the token) | Give the client the documented role. Never give a tenant client `tenants:manage`.                                                                         |
| `403` "Cannot grant …" or "Cannot manage …"               | The roles involved go beyond the caller's own                               | Use a client that holds those roles or `tenant:admin` ([granting roles](reference/roles.md#granting-roles)).                                               |
| Signed in, but actions fail with "… the backend could not be reached" | The backend stopped or is restarting, the network dropped, or the browser blocked the request for CORS (next row) | Open `<backend>/health` in the browser. If it does not answer, read `eudiplo logs --instance <name> --service eudiplo --tail 100`, then retry the action. |
| Browser console shows a CORS error for `/api/...`         | `CORS_ORIGINS` does not include the page's origin                           | Add the exact origin (`scheme://host[:port]`, no trailing slash) and run `eudiplo up`.                                                                    |

## Wallet connection

| Symptom                                                   | Cause                                                                       | Fix                                                                                                                                                       |
| --------------------------------------------------------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Wallet cannot open the offer or request                   | `PUBLIC_URL` is not reachable from the phone, or it changed after the offer was created | Check the health endpoint on the phone. Correct `PUBLIC_URL`, run `eudiplo up`, and create a new offer.                                       |
| Offers or metadata contain `localhost`                    | `PUBLIC_URL` is still the default                                           | Set `PUBLIC_URL` to the public HTTPS address and run `eudiplo up`.                                                                                        |
| Wallet rejects the issuer or verifier certificate         | The wallet does not accept self-signed certificates, or needs registrar certificates | Follow [Wallet and registrar requirements](trust/wallet-registrars.md). Do not weaken verification to get around it.                              |
| Wallet reports `invalid_dpop_proof` or a DPoP error       | The wallet does not send a valid DPoP proof, or the proof's key differs from the one bound earlier | Use a wallet with DPoP support, or relax the DPoP setting of the issuer. See [Authorization servers](issuance/authorization-servers.md). |
| Wallet reports a PKCE or `invalid_request` error at authorization | Since 9.0, authorization codes require PKCE with `S256`               | Use a wallet that sends an `S256` code challenge.                                                                                                         |

## Issuance

| Symptom                                                   | Cause                                                                       | Fix                                                                                                                                                       |
| --------------------------------------------------------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Session stays `active`                                    | The wallet never fetched the offer                                          | See [Wallet connection](#wallet-connection).                                                                                                              |
| Session stays `fetched`                                   | The credential was delivered, but the wallet sent no notification          | Nothing to fix; only a `credential_accepted` notification moves the session to `completed`.                                                               |
| `POST /api/issuer/offer` returns `409` for the claims      | The claims do not match the claim fields of the credential configuration    | Send every mandatory claim with the configured type. See [Claims](issuance/claims.md).                                                                     |
| Wallet gets `invalid_grant` or "The session has expired"  | The offer outlived its lifetime                                             | Create a new offer; adjust `offerLifetimeSeconds` if needed.                                                                                               |
| Wallet asks for a key attestation                         | The credential's supported proof types require one                          | Add proof type **JWT**, or use a wallet with key attestation.                                                                                             |
| "No key chain found with usage type ..."                  | The tenant has no key chain for that purpose                                | Create one under **Cryptographic Assets → Keys**.                                                                                                         |
| Token request answers `500` "The tenant's access token key chain is not available." | `token.signingKeyId` of the authorization server or the `accessToken` entry of `key-chain-defaults.json` names a key chain that does not exist or is not an access token key chain, as values stored before 10.0 do; or nothing names one and a key chain with ID `access-token` of another usage type blocks the one EUDIPLO creates. The backend log names the cause | Choose an Access Token Signing key, or remove the value to use the tenant's access token key chain; in the second case, create an Access Token Signing key. See [Access token key chain](trust/keys-and-certificates.md#access-token-key-chain). |
| Attribute provider or webhook is never called             | The URL is HTTP or private, which the outbound URL policy blocks by default | Use a public HTTPS URL. For local development only, set `OUTBOUND_URL_ALLOW_HTTP=true` and `OUTBOUND_URL_ALLOW_PRIVATE_NETWORK=true`.                     |
| "Failed to fetch authorization server metadata" or "Failed to fetch upstream OIDC configuration" | The external authorization server or the chained server's upstream provider is on HTTP or a private address, which the outbound URL policy blocks by default; the log names the rejected URL | Use a public HTTPS URL. For local development only, set `OUTBOUND_URL_ALLOW_HTTP=true` and `OUTBOUND_URL_ALLOW_PRIVATE_NETWORK=true`. |
| "Failed to authenticate with registrar: the outbound URL policy blocks a request to the OIDC provider", or a registrar URL rejected with `400` on save | The registrar, its OIDC provider or the token endpoint from its discovery document is on HTTP, a private address or a host outside `OUTBOUND_URL_ALLOWED_HOSTS` | Use public HTTPS URLs. For a registrar inside your network, set `OUTBOUND_URL_ALLOW_PRIVATE_NETWORK=true` (and `OUTBOUND_URL_ALLOW_HTTP=true` for plain HTTP), or add its hosts to `OUTBOUND_URL_ALLOWED_HOSTS`. See [Registrar](trust/registrar.md#1-connect-the-registrar). |
| "Failed to create access certificate: At least one registered contact value (support URI, email, or phone) is required." | The relying party at the registrar has no contact | Set **Relying Party Contact** in the registrar configuration before the relying party is registered. A relying party that is already registered keeps its contact: add it at the registrar. See [Registrar](trust/registrar.md#relying-party). |
| The credential in the wallet shows old values             | A wallet keeps the claims it was issued with                                | Issue a new credential after changing configuration or claims.                                                                                            |

## Presentation

| Symptom                                                   | Cause                                                                       | Fix                                                                                                                                                       |
| --------------------------------------------------------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Wallet finds no matching credential                       | Format, VCT or claim paths differ from the issued credential, or `trusted_authorities` excludes its issuer | Compare the DCQL query with the credential type. See [DCQL](presentation/dcql.md).                                              |
| Saving a presentation configuration fails with `Credential queries without trusted_authorities` | A credential query has no trust list or federation trust anchor | Add one under **Issuer trust**. See [DCQL](presentation/dcql.md#accept-only-trusted-issuers). |
| Wallet rejects the verifier                               | The access certificate is missing, inactive or not trusted by the wallet    | Select an active access key chain in the presentation configuration; see [Wallet and registrar requirements](trust/wallet-registrars.md).                 |
| Request rejected for overasking                           | The registration certificate does not cover every requested credential and claim | Update the registration certificate to match the DCQL query. An imported `jwt` that does not match is already refused when the configuration is saved. See [Registration certificates](trust/registration-certificates.md). |
| Wallet gets "The session has expired"                     | The request outlived its lifetime (default 300 seconds)                     | Generate a new request and approve it sooner, or raise the lifetime.                                                                                      |
| Session `failed` with `access_denied`                     | The user declined in the wallet                                             | Expected; offer a new request.                                                                                                                            |
| Session `failed` with `trust_chain_not_trusted` or `no_trust_chain_to_root` | The issuer is not on the trust lists of the credential query | Add the issuer to the trust list, or accept that the credential is rejected. See [Accept only trusted issuers](cookbooks/trusted-issuers.md). |
| Session `failed` with `trust_list_unavailable`            | A trust list could not be loaded (also when the outbound URL policy blocks its HTTP or private URL), has expired, or lacks verification material | Check the list URL, the backend log and its `verifierX509Der` or `verifierKey`. See [Trust lists](trust/trust-lists.md).                     |
| Session `failed` with "Status is not valid"               | The credential is revoked or suspended                                      | Expected after revocation. See [Revocable credentials](cookbooks/revocable-credentials.md).                                                              |
| No webhook arrives                                        | The endpoint is unreachable or blocked by the outbound URL policy, or it redirects to a URL the policy blocks (the log shows `redirectTarget`); webhooks are not retried | Check the backend log, then read the result with `GET /api/session/{id}`. See [Receive results](presentation/receive-results.md).          |
| Session shows `active` after its expiry time              | The `expired` status is written by a periodic cleanup job                   | Compare `expiresAt` with the current time instead of waiting for `expired`.                                                                              |
