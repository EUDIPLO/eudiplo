# Upgrading from 9.x to 10.0

Each section below says what changed in EUDIPLO 10.0 and what to do; skip the sections that do not apply to you.

## Before you upgrade

- Upgrade from any 9.x release. On 8.x or older, [upgrade to 9.x first](./index.md#upgrade-guides).
- If clients or people revoke or suspend credentials with only `issuance:offer`, plan when they get `credentials:status` ([Credential status](#credential-status-issuanceoffer-no-longer-revokes-or-suspends)).
- If you import a configuration folder at startup (`CONFIG_IMPORT_MODE=upsert` or `replace`), read [Configuration files](#configuration-files): unchanged key chains are no longer applied again, and unchanged `!generate` clients keep their secret.
- If you rely on OpenID Federation trust anchors, check your federation before you upgrade ([OpenID Federation](#openid-federation-trust-chains-are-verified)): self-asserted membership is no longer accepted.
- List your tenants (`GET /api/tenant`). A tenant whose ID is `.` or `..`, is `kms.json` in any letter case or contains `/` or `\` loses its configuration folder, including its own `kms.json`: move it to a tenant with a valid ID while you still run 9.x ([Tenants: IDs must be a folder name](#tenants-ids-must-be-a-folder-name)). If two tenants have IDs that differ only in case and `CONFIG_FOLDER` is on a case-insensitive file system (macOS, Windows), they share one folder: move one of them to a new tenant.
- Follow the [upgrade procedure](./index.md#upgrade-procedure).

## Operators

### Registrar requests follow the outbound URL policy

**Changed:** every request to the registrar API and its OIDC provider goes through the [outbound URL policy](../concepts/security-model.md#https-and-tls): the configured `registrarUrl` and `oidcUrl`, the token endpoint that the OIDC discovery document names, and every redirect target. 9.x called any URL, so a tenant with `registrar:manage` could reach internal services. Up to 5 redirects are followed; the access token only goes to the origin of the original request, and a request body, such as the token request with the password, never goes to another origin (a `303`, or a `301` or `302` after a `POST`, continues as a `GET` without body; any other such redirect fails). Each request must finish within 30 seconds, redirects included, and a response may have at most 5 MiB; 9.x had no limits. As long as the policy blocks the registrar, everything that calls it fails, including registrar enrollment of access certificates, schema metadata publication and OID4VP requests that need a new registration certificate.

**Do:** if the registrar or its OIDC provider runs on a private address or plain HTTP (for example a local registrar or Keycloak in a Compose network), set `OUTBOUND_URL_ALLOW_PRIVATE_NETWORK` or `OUTBOUND_URL_ALLOW_HTTP` to `true`, or move it to HTTPS on a public address. If `OUTBOUND_URL_ALLOWED_HOSTS` is set, add the registrar host, the OIDC host and the host of the token endpoint from the discovery document. Registrar requests now use `HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY` like webhooks ([proxies](../concepts/security-model.md#https-and-tls)); EUDIPLO still resolves the registrar hosts itself to check them, also behind a proxy. Details: [Registrar](../trust/registrar.md#1-connect-the-registrar).

### Client and user management: callers grant only their own roles

**Changed:** in 9.x, a token with `clients:manage` could give a client every role except `tenants:manage` and `tenant:admin`, whether it held that role or not. It could also change, delete or rotate the secret of any client of its tenant, including clients with more roles, such as the tenant's `<tenant>-admin` client. `users:manage` could do the same for people, including setting their password. 10.0 applies the [granting rules](../reference/roles.md#granting-roles) to `POST /api/client`, `PATCH /api/client/{id}`, `DELETE /api/client/{id}`, `POST /api/client/{id}/rotate-secret`, `POST /api/user`, `PATCH /api/user/{id}`, `DELETE /api/user/{id}` and configuration bundle imports:

- a caller grants only the roles it holds; with `tenant:admin` it grants every role except `tenants:manage` and `tenant:admin`, and only `tenants:manage` grants those two;
- a caller changes, deletes or rotates the secret of a client or person only if it holds or can grant each of its roles. With Keycloak, the roles assigned there count too, including those from groups, and a `realm-management` role or any other client role mapped directly to the account blocks the change.

Other requests answer HTTP `403`; a bundle plan already reports them. With Keycloak, a client that exists in Keycloak but not among EUDIPLO's clients of the tenant can no longer be changed, rotated or deleted through the API.

**Do:** before you upgrade, give every client or person that creates or changes clients or people each role it hands out, or `tenant:admin` to let it hand out every role except `tenants:manage` and `tenant:admin`. Manage accounts with Keycloak client roles in Keycloak. If a tenant's admin client misses a role after the upgrade, send `POST /api/tenant` again with the root client, the tenant's name and all roles it needs ([Tenants and access](../operate/tenants-and-access.md#create-a-tenant)); with the built-in authorization server this returns a new secret. With Keycloak you can also assign the role there; without it, a client file with the roles in the tenant's configuration folder and one start with `CONFIG_IMPORT_MODE=create` adds a client that has them ([Configuration as code](../operate/configuration-as-code.md#provision-tenants-from-a-folder)).

### Client IDs are unique across tenants

**Changed:** a client ID identifies one client across all tenants. In 9.x, creating a client with a taken ID could replace the existing client: with the built-in authorization server also one of another tenant or the root client, with Keycloak a client without `tenant_id`, such as the backend's own admin client. In 10.0, `POST /api/client` answers HTTP `409` for every taken ID, and `POST /api/tenant` when `<tenant>-admin` belongs to another tenant or the root client. A bundle plan blocks a client whose ID another tenant uses (`CLIENT_ID_TAKEN`), so the import stops before it changes anything; this includes the startup import of a tenant folder. Creating an existing tenant again still updates its own admin client.

**Do:** give clients of different tenants different IDs. Check startup configuration folders for the same `clientId` in two tenants. In scripts, treat `409` on `POST /api/client` as "ID taken".

### Deleting a client or changing its secret ends its access; `JWT_EXPIRES_IN` removed

**Changed:** with the built-in authorization server, deleting a client or its tenant ends the client's API access at once, and role changes apply to the tokens it already has; in 9.x its tokens worked until they expired. A new client secret also ends the tokens issued with the old one: `POST /api/client/{id}/rotate-secret`, `POST /api/tenant` with `roles` for an existing tenant (new secret for `<tenant>-admin`), a configuration bundle import with another secret or `!generate`, and a startup import with another secret, including a client file without `secret`, which gets a new random secret on every start in `upsert` or `replace` mode. In 9.x, the old tokens kept working for up to 24 hours. Creating a deleted client or tenant again with the same ID does not revive the old tokens either. Importing the secret a client already has keeps its tokens. With Keycloak, a deleted client's tokens stay valid until the realm's access token lifespan ends. `JWT_EXPIRES_IN` is removed: 9.x documented it as the token lifetime, but tokens always lived 24 hours. 10.0 ignores a leftover value.

**Do:** to cut off a leaked token, rotate its client's secret or delete the client; with Keycloak, both leave issued tokens valid until the realm's access token lifespan ends ([Revoke access](../operate/tenants-and-access.md#revoke-access)). If an integration relied on its old token to keep working after a secret rotation, have it request a new token right after the rotation, or create a second client, switch the integration to it and delete the first one. Remove `JWT_EXPIRES_IN` from your `.env`, Compose files and Kubernetes manifests.

### `CRYPTO_ALG` removed

**Changed:** `CRYPTO_ALG` is removed. 9.x accepted only `ES256` for it; in 10.0 each key chain signs with the algorithm of its curve, chosen when it is created or with `defaultAlgorithm` in `kms.json` ([Signing algorithms](../operate/kms.md#signing-algorithms)). 10.0 ignores a leftover value.

**Do:** remove `CRYPTO_ALG` from your `.env`, Compose files and Kubernetes manifests.

### Access tokens: signed by their own key chain

**Changed:** the built-in, chained and OID4VP authorization servers sign access tokens only with a key chain of the new usage type `accessToken`, and their JWKS publishes only its keys. 9.x used `token.signingKeyId`, then (built-in server only) the issuance configuration's `signingKeyId`, then whichever signing key chain the database returned first: often the registrar access certificate or a credential signing key, and a token request failed with `Failed to create access token response` when that key chain could not sign. Now an authorization server without `token.signingKeyId` uses the `accessToken` entry of the tenant's key chain defaults, else the tenant's oldest access token key chain; on the first token request after the upgrade, EUDIPLO creates a standalone key chain `access-token` for it with the tenant's default KMS provider. Its key in an external KMS is named `<random UUID>-active`, so a KMS policy that limits key names or creation must allow it. Its key replaces the key in the JWKS, so an access token issued by 9.x and presented after the upgrade is refused once; the wallet requests a new one. The JWKS keeps the previous key for one token lifetime after a rotation of the key chain ([Access token key chain](../trust/keys-and-certificates.md#access-token-key-chain)).

The issuance configuration's `signingKeyId` is removed: the database migration drops a stored value and logs it. `token.signingKeyId` must name a key chain with usage type `accessToken`. The migration does not change a stored `token.signingKeyId`, and every value from 9.x names another usage type: until you change it, that authorization server answers token requests with `500` while the backend log names the key chain. If a tenant already has a key chain with ID `access-token` and another usage type, EUDIPLO cannot create its key chain, and token requests fail the same way.

**Do:**

- Remove `token.signingKeyId` from the authorization servers of your issuance configurations, or point it to a key chain with usage type `accessToken` (in the Web Client: **Access Token Signing Key** of the authorization server).
- To choose one key chain for all authorization servers of a tenant, set `accessToken` in `key-chain-defaults.json`.
- If a tenant has a key chain with ID `access-token` that is not an access token key chain, create an access token key chain for it.
- Registrar access certificates and credential signing key chains no longer need to be kept for access tokens.

### Issuer registration certificates list `vct` and `docType`

**Changed:** in `registrationCertificate.mode: "generate"`, `provides_attestations` lists the `vct` of every SD-JWT VC credential configuration (the hosted VCT URL for a `vct` object) and the `docType` of every mDOC configuration, as the registrar expects. 9.x sent the schema metadata IDs (`schemaMeta.id`) and left out configurations without `schemaMeta`. After the upgrade, the first metadata request of each tenant in `generate` mode requests a new certificate and revokes the cached one if it is still valid.

**Do:** nothing, unless the registrar refuses a listed type: the metadata is then served without `issuer_info` and the reason is logged. Details: [Registration certificates](../trust/registration-certificates.md#issuer-registration-certificate).

### Wallet attestations: unreadable status lists are rejected

**Changed:** when a wallet attestation has a `status` claim, the PAR and token endpoints of the built-in, chained and OID4VP authorization servers reject it if the claim is malformed (not a JSON object, an empty object, or a `status_list` without a non-empty string `uri` or a non-negative integer `idx`; 9.x treated it as absent), if its status list was fetched but cannot be read, is not typed `statuslist+jwt`, does not carry the attestation's status list URI as `sub`, has no `iat` or has expired, or if its index is outside the list. A status list whose signature does not verify is rejected too; 9.x accepted a forged signature under a genuine `x5c`. A status list must also be signed under the provider's revocation certificate (a `WalletSolution/Revocation` or `EAA/Revocation` service), or under its attestation certificate if it lists neither; 9.x accepted any key in the list's own `x5c` for a provider without a revocation certificate. The answer says `Wallet attestation status list rejected: ...` with the reason, `Status list JWT signature verification failed ...` for a bad signature or signer, or `Wallet attestation status check failed` for other errors, including a malformed claim. This is the answer of the built-in token endpoint; the PAR endpoints and the token endpoints of chained and OID4VP authorization servers answer `invalid_client` with `Client attestation validation failed` ([below](#wallet-attestations-chained-and-oid4vp-authorization-servers-answer-invalid_client)), and the server log has the reason there. 9.x rejected revoked and suspended attestations, status lists without `x5c` and lists chained to a certificate other than the provider's revocation certificate, but logged every other status check failure and accepted the attestation. A status list that cannot be fetched (network error, timeout, non-2xx answer, URL blocked by the outbound URL policy) is still accepted with a warning: that is the default mode `best_effort` of the new setting `walletAttestationStatusCheckMode`, on the issuance configuration and on each authorization server. `strict` also rejects a list that cannot be fetched; `disabled` skips the status check, so revoked and suspended attestations are accepted as well. There is no mode that accepts an unreadable list but still rejects revoked attestations.

**Do:** if wallets fail with one of these messages, look up the reason in the server log and check the wallet provider's list at the attestation's `status.status_list.uri`. Set `walletAttestationStatusCheckMode: "disabled"` only if you accept revoked wallet instances. Details: [Wallet and key attestation](../trust/attestation.md#2-require-wallet-attestation).

### OpenID Federation: trust chains are verified

**Changed:** 9.x trusted any entity whose entity configuration named a configured trust anchor in `authority_hints`, without checking a signature against the trust anchor, and accepted unsigned entity configurations. 10.0 resolves and verifies the whole trust chain ([OpenID Federation](../trust/federation.md#how-trust-is-decided)):

- An external or upstream authorization server with a `federation` policy must be listed in a signed subordinate statement by the trust anchor or an intermediate below it, and its entity configuration must have `oauth_authorization_server` or `openid_provider` metadata whose `issuer` is its entity ID.
- A presented SD-JWT VC whose query has only an `openid_federation` trusted authority must have an `iss` claim naming the issuer entity and a `kid` header naming a key in the entity's `openid_credential_issuer` metadata (`jwks`), and be signed with that key. 9.x took the entity ID from the `x5c` leaf certificate and never checked that the certificate's key belongs to the entity, so anyone could present a credential under a member's name; that certificate is no longer used. Its status list must be signed with a key of the same entity's metadata.
- An mDOC whose query has only an `openid_federation` trusted authority is rejected. A query with an `etsi_tl` entry as well keeps working through the trust list.
- Federation requests verify TLS certificates also outside `NODE_ENV=production`, and an entity configuration or fetch endpoint must answer with `application/entity-statement+jwt`.
- Session outcomes and webhooks report a federation trust failure of an SD-JWT VC as `no_trust_chain_to_root` (no valid chain, or no key `kid`) or `trust_list_unavailable` (federation unreachable) instead of `verification_error`.
- A failed verification is no longer replaced by a cached result from the last hour; only when the federation cannot be reached is the last successful resolution reused, for at most 15 minutes and until its chain expires.
- Every trust anchor must be registered with its federation keys (`POST /api/federation-trust-anchor`, or `federation-trust-anchors/<id>.json` in the config folder), and its entity configuration must be signed with one of them. Configurations stored before the upgrade keep loading, but nothing is trusted through an unregistered trust anchor: authorization servers are refused and credentials fail with `no_trust_chain_to_root`, and the log says `no trust anchor of <entity IDs> is registered with pinned keys`. Importing or creating an issuance configuration whose `federation.trustAnchors`, or a presentation configuration whose `openid_federation` values (in queries without an `etsi_tl` entry), name an unregistered entity ID is rejected with `400`, also at startup import; so is a change that adds one. Other changes to a stored configuration keep working.

**Do:** before you upgrade, get each trust anchor's federation keys from its operator through a channel you trust. If you import configuration from a config folder, add a `federation-trust-anchors/<id>.json` file for each trust anchor to every tenant folder that names it before you start 10.0, or the plan of that tenant's startup import is blocked, and applies nothing, as soon as a new or changed document names an unregistered trust anchor. Otherwise register them right after the upgrade with `POST /api/federation-trust-anchor` ([Register trust anchors](../trust/federation.md#register-trust-anchors)). Check that every federation entity you rely on is registered with its trust anchor (or an intermediate) and publishes signed statements; test with `GET {entityId}/.well-known/openid-federation` and the superior's fetch endpoint. Issuers whose SD-JWT VCs you verify through federation must set `kid` and publish the key in their `openid_credential_issuer` metadata. Add an `etsi_tl` trust list to mDOC queries that only name a trust anchor. Update alerting or code that matched `verification_error` for federation failures. For federation entities with test certificates outside production, use certificates EUDIPLO trusts (`NODE_EXTRA_CA_CERTS`). To delegate resolution to a trust engine, set `FEDERATION_RESOLVER=http` ([Choose the resolver](../trust/federation.md#choose-the-resolver)).

### HTTP request log: wallet references redacted, `req.walletNonce` removed

**Changed:** the HTTP request log no longer has the `req.walletNonce` field that 9.0 added for the OID4VP routes. Logged URLs replace the wallet reference in `/issuers/{tenant}/vci/credential-offers/{walletNonce}`, `/presentations/{walletNonce}/oid4vp/...`, `/presentations/{walletNonce}/iso-18013-7` and `/issuers/{tenant}/authorize/interactive/complete-web-auth/{auth_session}` with `[redacted]`, and so does the `url.path` span attribute. The values of the query parameters `issuer_state`, `request_uri`, `code` and `response_code` are `[redacted]` in logged URLs and in `url.query`, like `q` in 9.x. Whoever read these values in a log or trace could fetch the offer, answer the presentation request or continue the authorization.

**Do:** change log queries, dashboards and alerts that use `req.walletNonce` or these path and query values to `sessionId` and `tenantId`, which every log line of a request carries once it resolved its session ([Correlate logs with sessions](../operate/logging.md#correlate-logs-with-sessions)).

## Integrators

### OpenID Federation: SD-JWT VCs need `iss` and `kid`, new failure codes

**Changed:** a presented SD-JWT VC whose query names only an OpenID Federation trust anchor is verified with the key `kid` of its issuer's federation metadata, not with its `x5c` certificate; mDOCs are rejected for such queries. Session outcomes and webhooks report these federation failures as `no_trust_chain_to_root` or `trust_list_unavailable` instead of `verification_error`.

**Do:** see [OpenID Federation: trust chains are verified](#openid-federation-trust-chains-are-verified) under Operators.

### Wallet attestations: chained and OID4VP authorization servers answer `invalid_client`

**Changed:** the PAR and token endpoints of chained and OID4VP authorization servers answer a rejected wallet attestation, including a missing one where it is required, with an OAuth error (RFC 6749 Section 5.2), as the built-in authorization server does: `error: "invalid_client"` and `error_description: "Client attestation validation failed"`, with HTTP 400 at the PAR endpoint and HTTP 401 at the token endpoint. 9.x answered HTTP 401 at both endpoints with `error: "Unauthorized"` and a `message` that named the reason. The reason is now only in the server log.

**Do:** if a wallet or test client of a chained or OID4VP authorization server checks the HTTP status or `message` of a rejected attestation, check for `error: "invalid_client"` instead. Look up the reason in the server log ([troubleshooting](../trust/attestation.md#troubleshooting)).

### Issuance configuration: `signingKeyId` removed, `accessToken` key chains

**Changed:**

- `POST /api/issuer/config` refuses the top-level `signingKeyId` with `400`, `GET` no longer returns it, and the `@eudiplo/sdk-core` types `IssuanceConfig` and `UpdateIssuanceDto` drop it.
- A `token.signingKeyId` that a request sets or changes must name a key chain with usage type `accessToken`, else `400`.
- Key chain `usageType` gains `accessToken`, and key chain lists can contain the `access-token` key chain EUDIPLO creates ([Access tokens](#access-tokens-signed-by-their-own-key-chain)).
- `DefaultKeyChains` (`key-chain-defaults.json`) gains `accessToken`.

**Do:** stop sending `signingKeyId` in issuance configuration requests, create access token key chains for `token.signingKeyId` (`POST /api/key-chain` with `"usageType": "accessToken"`), and handle `accessToken` wherever your code switches on `usageType`.

### Issuance: offers name their session with a random value, not the session ID

**Changed:** in 9.x, the `credential_offer_uri` ended with the session ID, an authorization code offer carried the session ID as `issuer_state`, and an external authorization server copied it into its access tokens. The session ID is also what `POST /api/issuer/offer` returns, `GET /api/session` lists, and webhooks and the audit log contain, so anyone who saw it could fetch the offer before the holder's wallet or start its authorization. In 10.0, each new issuance session gets a random `walletNonce`: the `credential_offer_uri` ends with it, `issuer_state` is it, and the offer URI endpoint, pushed authorization requests of the built-in, chained and OID4VP-based authorization servers, interactive authorization and external token bindings find the session only by it. The session ID answers `404` at the offer URI endpoint HTTP `400` "Invalid issuer_state" at the chained and OID4VP-based authorization servers and `invalid_request` at interactive authorization; the built-in server's pushed authorization request treats it like any unknown `issuer_state` and starts a wallet-initiated authorization without the offer; an external token whose binding claim holds the session ID gets `credential_request_denied` at the credential endpoint (9.x answered an external token bound to no offer with HTTP `500`). The migration sets `walletNonce` to the session ID for offers that exist before the upgrade, so they keep working. Offers that a 9.x instance creates after the migration ran get no `walletNonce`, so do not run 9.x and 10.0 instances against the same database at the same time. Built-in access tokens keep the session ID as `sub`, and chained tokens keep it as `issuer_state` claim.

**Do:** pass the wallet only the offer URI from `POST /api/issuer/offer`. If your code builds a `credential_offer_uri` or an `issuer_state` from the session ID, take the value from the offer URI instead (`walletNonce` of `GET /api/session/{id}`). If your external authorization server maps `issuer_state` to EUDIPLO session IDs, look the session up by `walletNonce` or stop relying on that mapping.

### ISO 18013-7: the page posts to the `response_uri`, not to the session ID

**Changed:** in 9.x, the page posted the wallet's encrypted response to `POST /presentations/{session}/iso-18013-7` with the session ID from `POST /api/verifier/offer`. The session ID is also what `GET /api/session` lists and webhooks and the audit log contain, so anyone who saw it could post a response in the holder's place and end the session as failed. In 10.0, an offer with `response_type: "iso-18013-7"` returns `org_iso_mdoc.response_uri`, which ends with a random `walletNonce`, and the endpoint finds the session only by it. The session ID answers `404`. The migration sets `walletNonce` to the session ID for ISO 18013-7 sessions that exist before the upgrade, so pages that already hold an offer can finish it. ISO 18013-7 sessions that a 9.x instance creates after the migration ran get no `walletNonce` and answer `404`, so do not run 9.x and 10.0 instances against the same database at the same time. The OpenID4VP endpoints do not answer an ISO 18013-7 `walletNonce`.

**Do:** post the encrypted response to `org_iso_mdoc.response_uri` from the offer response instead of building the URL from `session`. Keep using `session` for `GET /api/session/{id}` and webhooks.

### Issuance: presentation steps have their own session ID

**Changed:** in 9.x, the presentation session of an [interactive authorization](../issuance/interactive-authorization.md) step had the `auth_session` as ID, and `GET /api/session` lists it, so anyone who saw it could send the follow-up request after the wallet had answered at the `response_uri` and take the only authorization code. In 10.0, each presentation step gets a presentation session with a random ID; `GET /api/session/{auth_session}` answers `404`. The migration keeps auth sessions that are open during the upgrade working; presentation steps that a 9.x instance starts after the migration ran fail with `invalid_request` on 10.0, so do not run both versions against the same database at the same time. The callback of the [OID4VP-based authorization server](../issuance/authorization-servers.md#oid4vp) (`…/vp-callback?cas=…`) now answers HTTP `400` and leaves the authorization pending when it gets no matching `response_code` while the presentation is open or has completed; 9.x ended the authorization and redirected with an error. It still redirects with an error once the presentation failed or expired.

**Do:** if your backend reads the presentation session of an interactive authorization step by its `auth_session`, look it up by the walletNonce of the step's `request_uri` instead (`GET /api/session?q=…`).

### Registrar configuration: URLs checked on save

**Changed:** `POST` and `PATCH /api/registrar/config` answer HTTP `400` for a `registrarUrl` or `oidcUrl` that is not a plain `http(s)` base URL (with a query, a fragment, also a trailing `?` or `#`, or credentials) or that the outbound URL policy blocks; `errors[].path` names the field. A `PATCH` also checks stored URLs it leaves out against the outbound URL policy; the base URL rule applies to the URLs it sends. A `PATCH` that changes `registrarUrl` also needs `password` (see below). The credential check answers `400` if the token endpoint from the discovery document or a redirect target is blocked. Unless `OUTBOUND_URL_ALLOW_PRIVATE_NETWORK` is set, the policy check resolves both hosts, so an OIDC host that cannot be resolved now answers `400` instead of `503`, and the `registrarUrl` host must resolve as well.

**Do:** send base URLs without query, fragment or credentials, and show the error at the field named in `errors[].path`. A stored configuration whose URL has a query, fragment or credentials keeps being used until it is replaced with `POST` or a `PATCH` that sends the URL; the Web Client marks such a URL on the Registrar Config page and saves only after it is fixed. An export of such a tenant fails the import plan until the URL is fixed.

### Issuance configuration: `federation.entityId` checked on save

**Changed:** `POST /api/issuer/config` answers `400` for a non-empty `federation.entityId` that is no `https` URL with a host and without query, fragment, credentials or whitespace (`http` only with `OUTBOUND_URL_ALLOW_HTTP=true`), also when the request changes other fields and sends the stored value back.

**Do:** see [Issuance configuration: `federation.entityId` must be an https URL](#issuance-configuration-federationentityid-must-be-an-https-url) under Configuration files.

### Credential configurations: claim patterns run on RE2

**Changed:** claim `constraints` patterns (`pattern`, `patternProperties` keys, `propertyNames.pattern`) are matched with RE2 in linear time; 9.x used the JavaScript engine, where a pattern like `^(a+)+$` could block issuance for all tenants. `POST /api/issuer/credentials` and `PATCH /api/issuer/credentials/{id}` answer `400` with "Claim patterns are matched with RE2" for a pattern RE2 cannot run: lookarounds (`(?=`, `(?!`, `(?<=`, `(?<!`), backreferences (`\1`, `\k<name>`), inline flags such as `(?i)`, unknown escapes such as `\e`, `\S` inside a character class, the empty classes `[]` and `[^]`, long Unicode property names such as `\p{Letter}` or `\p{Script=Latin}`, patterns over 1000 characters and patterns with too many or too large repetitions. `\s`, `\S` and `.` keep their JavaScript meaning. A configuration stored by 9.x keeps its pattern: until it is replaced, offers with claims for it answer `409` and credential requests fail with `credential_request_denied`, both with "has a claim pattern that cannot be used", and a save that sends it back, as the Web Client does, answers `400`.

**Do:** search your credential configurations for the constructs above and rewrite them, for example `\p{L}` for `\p{Letter}`, `\p{Latin}` for `\p{Script=Latin}` or an explicit character class for a lookahead; see [Constraints](../issuance/claims.md#constraints). Configuration files: see [Credential configurations: claim patterns must suit RE2](#credential-configurations-claim-patterns-must-suit-re2).

### Credential status: `issuance:offer` no longer revokes or suspends

**Changed:** `POST /api/session/revoke` needs the new role `credentials:status` or `issuance:manage`. In 9.x, `issuance:offer` could also revoke, suspend and reinstate the credentials of every issuance session of its tenant, so every client that creates offers could invalidate credentials. A token with `issuance:offer` but neither of the two roles now gets HTTP `403`. Reading the status with `GET /api/session/{id}/credential-status` still works with `issuance:offer`. In the Web Client, the **Revoke**, **Suspend** and **Reinstate** buttons of a session's **Credential Status** card need `credentials:status` or `issuance:manage`. With Keycloak, EUDIPLO creates the realm role at the first start of 10.0, together with the new roles `audit:read`, `sessions:read` and `keys:manage`, which need no action ([roles](../reference/roles.md)).

**Do:** give `credentials:status` to every client and person that changes credential status with only `issuance:offer`, for example your application backend. A caller grants it only if it holds it or has `tenant:admin` ([granting roles](../reference/roles.md#granting-roles)); to give it to a tenant's admin client first, see [Client and user management](#client-and-user-management-callers-grant-only-their-own-roles). Client files with the new roles need file format v2 ([Configuration files](#configuration-files)).

- **Built-in authorization server:** 9.x rejects the new role, so you can grant it only once 10.0 runs. Until then, revocations of those clients answer `403`. Grant it right after the first 10.0 instance is healthy and before it takes traffic, or plan for that window.
- **Keycloak:** create the realm role `credentials:status` and assign it before the upgrade; 9.x passes it through, and 10.0 keeps the existing role. Until 10.0 runs, do not edit these clients or people through EUDIPLO 9.x, in the API or the Web Client: 9.x removes realm roles it does not know when it saves them.

### Tenants: IDs must be a folder name

**Changed:** a tenant ID is also the name of the tenant's folder in `CONFIG_FOLDER`. 9.x accepted any non-blank ID in `POST /api/tenant`, so an ID such as `x/../acme` pointed to the folder of the tenant `acme`: its admin could read and change that tenant's `kms.json` and reattach its file-managed resources, with their secrets, into its own tenant. IDs that differ only in case, such as `Acme`, share that folder on case-insensitive file systems, and the ID `kms.json` named the global KMS file. In 10.0, `POST /api/tenant` answers `400` unless the ID uses only lowercase letters, digits, `-` and `_`, starts with a letter or digit and has at most 63 characters, the rule `eudiplo config tenant create` already applied; leading and trailing spaces are still trimmed. Existing tenants keep their ID, but sending `POST /api/tenant` again for one whose ID breaks the rule, for example to give its `<tenant>-admin` client other roles, answers `400`. The startup import still creates tenants from folder names that break the rule, except a folder whose name contains `\` or is `kms.json`, which it skips with a warning. A tenant whose ID is `.`, `..` or `kms.json` (in any letter case) or contains `/`, `\` or NUL has no configuration folder: EUDIPLO uses the global `kms.json` for it and no longer reads `<CONFIG_FOLDER>/<id>/kms.json`, `GET /api/key-chain/providers/config` returns `tenantConfig: null`, `PUT` and `DELETE` answer `400`, a bundle plan with a `KmsConfig` document is blocked (`KMS_CONFIG_FOLDER_MISSING`), and reattaching a resource answers `409`. With the startup import enabled (`CONFIG_IMPORT_MODE` other than `disabled`), the backend logs a warning for such a tenant at startup.

**Do:** use IDs such as `acme` or `acme-test` when you create tenants, and treat `400` from `POST /api/tenant` as an invalid ID. For an existing tenant whose ID breaks the rule, change its admin client with `PATCH /api/client/<tenant>-admin` and `POST /api/client/<tenant>-admin/rotate-secret` instead of sending `POST /api/tenant` again. Before you upgrade, move each tenant that will have no configuration folder to a new tenant with a valid ID: export its configuration bundle on 9.x and import it into the new tenant. After the upgrade, 10.0 no longer loads the providers of its own `kms.json`, so key chains that use them stop working.

### Client API: `404` for unknown clients

**Changed:** with the built-in authorization server, `PATCH /api/client/{id}` for a client the tenant does not have answers `404` instead of `200`. With Keycloak, `POST /api/client/{id}/rotate-secret` for such a client answers `404` instead of `500`. For `403` and `409` from the client and user endpoints, see [Client and user management](#client-and-user-management-callers-grant-only-their-own-roles) and [Client IDs are unique across tenants](#client-ids-are-unique-across-tenants).

**Do:** treat `404` as "no such client" in scripts that update clients or rotate their secrets.

### Management API tokens: no refresh token, checked against the client

**Changed:** with the built-in authorization server, `POST /api/oauth2/token` no longer returns `refresh_token`, and the property is gone from `TokenResponse` in the OpenAPI document and `@eudiplo/sdk-core`. In 9.x it was a second token with the same claims, valid for 30 days; the endpoint never accepted it for a refresh, but the API accepted it as a bearer token. 10.0 answers `401` to it, also to those issued by 9.x; access tokens issued by 9.x stay valid until they expire. Tokens of deleted clients, of clients with a new secret and roles removed from a client stop working at once ([Deleting a client or changing its secret ends its access](#deleting-a-client-or-changing-its-secret-ends-its-access-jwt_expires_in-removed)). With Keycloak, nothing changes besides a `401` for a token whose client ID now belongs to another tenant.

**Do:** request a new token with the client credentials when the old one expires, as the Web Client, the CLI and `@eudiplo/sdk-core` do, and stop using `refresh_token`. Details: [Revoke access](../operate/tenants-and-access.md#revoke-access).

### Webhooks and attribute providers: time and size limits, checked redirects

**Changed:** 9.x waited without limit for a webhook or attribute provider, read answers of any size, followed up to 21 redirects without checking their targets against the outbound URL policy, and sent the API key header to every redirect target. 10.0 ends a delivery after 60 seconds, redirects included, and reads at most 5 MiB of the answer. It follows up to 5 redirects (`301`, `302`, `303`, `307`, `308`); each target must pass the [outbound URL policy](../concepts/security-model.md#https-and-tls), and the API key header is only sent to the origin of the configured URL.

**Do:** configure the final URL of the webhook instead of one that redirects, for example `https://` instead of an `http://` URL that redirects, or the trailing slash your framework expects. Answer within 60 seconds; an attribute provider that needs longer answers `{"deferred": true}` ([Deferred issuance](../issuance/deferred-issuance.md)). Keep answers under 5 MiB. Details: [Webhooks](../reference/webhooks.md#delivery).

### Schema metadata: publishing needs `registrar:manage` as well

**Changed:** `POST /api/schema-metadata/publish` and `POST /api/schema-metadata/publish-version` need both `issuance:manage` and `registrar:manage`. 9.x accepted a token with only `issuance:manage`, although publishing uses the tenant's registrar credentials. A token with only `issuance:manage` now gets HTTP `403`, as one with only `registrar:manage` already did. Web Client users are not affected: the **Registrar → Schema** pages already need `registrar:manage`.

**Do:** give API clients and users that publish schema metadata both roles ([API clients with least privilege](../operate/tenants-and-access.md#api-clients-with-least-privilege)). Details: [Registrar](../trust/registrar.md#schema-metadata-ts11).

### Inline webhooks: empty URL, header name or API key rejected

**Changed:** the inline `webhook` of `POST /api/verifier/offer` and a `webhook` claim source in `credentialClaims` of `POST /api/issuer/offer` are validated like stored webhooks. An empty `url`, `auth.config.headerName` or `auth.config.value` now answers HTTP `400`. In 9.x the request was accepted; an empty URL or header name failed later at delivery, and an empty API key was sent as an empty header.

**Do:** send a non-empty `url`, header name and API key, or use `"auth": { "type": "none" }` for a webhook without authentication.

### Registrar: credentials required for a new OIDC or registrar URL

**Changed:** in 9.x, `PATCH /api/registrar/config` with a new `oidcUrl` checked the stored password and client secret against the token endpoint of the new URL, and a new `registrarUrl` received a token obtained with them. Whoever held `registrar:manage` could send the stored credentials to a server of their choice without knowing them. 10.0 answers `400` to a `PATCH` that changes `oidcUrl` or `registrarUrl` unless it also sends `password`, and `clientSecret` if one is stored; a new `registrarUrl` alone is therefore checked against the OIDC endpoint too and can answer `503` when it is unreachable. `POST /api/registrar/config` without `clientSecret` now removes a stored client secret; 9.x kept it. For configuration bundles and `registrar.json`, see [Registrar: imports remove omitted optional fields](#registrar-imports-remove-omitted-optional-fields-and-skip-the-credential-check).

**Do:** send `password`, and `clientSecret` if `hasClientSecret` is `true`, in every `PATCH` that changes `oidcUrl` or `registrarUrl`; in the Web Client, enter the password again after changing either URL, and the client secret if the registrar needs one. To drop a client secret, replace the configuration with `POST` without `clientSecret`, and send `registrationCertificateDefaults` along to keep them. Details: [Registrar](../trust/registrar.md).

### Registrar: `POST` removes omitted certificate defaults

**Changed:** in 9.x, `POST /api/registrar/config` kept stored `registrationCertificateDefaults` that the request left out. 10.0 removes them, like an omitted `clientSecret`; `PATCH` still changes only the fields it sends.

**Do:** send `registrationCertificateDefaults` in every `POST` that should keep them, or change single fields with `PATCH`. Details: [Registrar](../trust/registrar.md#1-connect-the-registrar).

### Key chains: enabled rotation needs `intervalDays`

**Changed:** `POST /api/key-chain` with `"rotationPolicy": { "enabled": true }` and without `intervalDays` answers HTTP `400`. So does `PUT /api/key-chain/{id}` with `"rotationPolicy": { "enabled": true }` when neither the request nor the key chain has a rotation interval, also for a key chain whose rotation is already enabled. 9.x accepted both and stored rotation as enabled, but the daily rotation job skips a key chain without an interval, so such a key chain was only rotated on request.

**Do:** send `intervalDays` whenever you enable rotation, or leave rotation off for key chains you rotate by hand. Key chains that already have rotation enabled without an interval keep their settings; `GET /api/key-chain` lists them with `rotationPolicy.enabled: true`, `intervalDays: null` and no `nextRotationAt`. Their export from `GET /api/key-chain/{id}/export` is imported again with a 90-day interval. Decide for each of them:

- Turn rotation off with `PUT /api/key-chain/{id}` and `"rotationPolicy": { "enabled": false }`, in particular for key chains whose certificate comes from a registrar or an external PKI: rotating a standalone or imported key chain replaces its certificate with a self-signed one.
- Or give it an interval with `"rotationPolicy": { "intervalDays": 90 }`. The daily job counts the interval from the last rotation or, without one, from creation, so a key chain older than the interval rotates in the next run.

Details: [Keys and certificates](../trust/keys-and-certificates.md#rotate-keys).

### Key chains: ES384 and ES512, and the algorithm lists in metadata

**Changed:** key chains can sign with ES384 (P-384) or ES512 (P-521) besides ES256, chosen with `alg` when they are created ([Keys and certificates](../trust/keys-and-certificates.md#create-a-key-chain)); ES256 stays the default. EUDIPLO accepts ES384 and ES512 from wallets and other issuers: `proof_signing_alg_values_supported` in the issuer metadata and the algorithm lists in `vp_formats_supported` of OID4VP requests now list ES256, ES384 and ES512 (mdoc: their COSE identifiers).

**Do:** nothing for ES256 key chains. Before you create ES384 or ES512 key chains, check that the wallets and relying parties you serve support them; wallets only have to support ES256.

### mdoc: algorithm identifiers in metadata and signature checks

**Changed:** three things follow OpenID4VCI 1.0, OpenID4VP 1.0 and RFC 9053 more closely for mdoc credentials:

- `credential_signing_alg_values_supported` of an mdoc credential configuration lists only the COSE identifier that EUDIPLO writes into the IssuerAuth `alg` header, for example `[-7]` instead of `[-7, -9]` for an ES256 key chain (OpenID4VCI 1.0 Appendix A.2.2). The credentials themselves are unchanged.
- In OID4VP requests, `client_metadata.vp_formats_supported.mso_mdoc` replaces `alg`, which OpenID4VP does not define, with `issuerauth_alg_values` (`[-7, -35, -36]`) and `deviceauth_alg_values` (`[-7, -35, -36, -9, -51, -52]`) (OpenID4VP 1.0 Appendix B.2.2). Wallets that read the old `alg` member no longer find it; wallets that follow OpenID4VP 1.0 now see the algorithms EUDIPLO accepts.
- A presented mdoc fails verification when its IssuerAuth or DeviceSignature has no `alg` in the protected header (ISO/IEC 18013-5 requires it), or when the `alg` names a different curve than the key, for example `-7` (ES256) on a P-384 key. The same applies to the status list and identifier list CWTs its MSO refers to. 9.x picked the hash from the key's curve and ignored the `alg`. The verification error names the mismatch.

**Do:** nothing for wallets that follow ISO/IEC 18013-5 and OpenID4VP 1.0. If a wallet relied on `vp_formats_supported.mso_mdoc.alg`, or omitted `alg` in its DeviceSignature, or an mdoc issuer omits `alg` in its status list CWTs, test it against 10.0 before you upgrade.

### Key chains: `activeCertificate` must be a PEM chain for the active key

**Changed:** `PUT /api/key-chain/{id}` with `activeCertificate` answers HTTP `400` for a value without a `-----BEGIN CERTIFICATE-----` block (an empty string included), for a block that is not a certificate, for a first certificate that does not hold the public key of the active key, and for a chain in which a certificate did not issue the one before it. 9.x stored any string, but EUDIPLO signs with the active key, so wallets could not verify a chain whose leaf belongs to another key. Registrar enrollment stores its certificate the same way; a certificate issued for a key that was rotated in the meantime is now refused and revoked at the registrar.

**Do:** send PEM, the certificate for the active key first, each certificate followed by the one that issued it; convert DER with `openssl x509 -inform der -in cert.der`. After a rotation, the key is new: create a certificate signing request with `GET /api/key-chain/{id}/csr` and store the certificate issued for it instead of the old one.

Details: [Keys and certificates](../trust/keys-and-certificates.md#request-a-certificate-with-a-csr).

### Key chains: the tenant's encryption key chain answers `404` and `409`

**Changed:** every tenant has an encryption key chain with usage type `encrypt`, which EUDIPLO creates itself and uses to decrypt encrypted credential requests and ISO 18013-7 responses. Its ID is the `kid` of the published encryption key. `GET /api/key-chain` never listed it, but 9.x let the other key chain endpoints change, rotate, delete and export it, and an import with its ID replaced it. In 10.0, `PUT /api/key-chain/{id}`, `POST /api/key-chain/{id}/rotate`, `DELETE /api/key-chain/{id}` and `GET /api/key-chain/{id}/export` answer HTTP `404` for its ID, and `POST /api/key-chain/import` with its ID answers `409`. `GET /api/key-chain/{id}` still returns its public key. The daily rotation job no longer rotates it, even if rotation was enabled for it.

**Do:** leave the encryption key chain to EUDIPLO; there is no replacement for rotating, deleting or exporting it. If `GET /api/key-chain?usageType=encrypt` lists a key chain whose ID is the `kid` of the published encryption key, a 9.x import replaced the encryption key chain. EUDIPLO still decrypts with it, but it is a normal key chain that the API can change. Details: [Keys and certificates](../trust/keys-and-certificates.md#usage-types).

### Trust lists: `DELETE` refuses lists that configurations use

**Changed:** `DELETE /api/trust-list/{id}` answers HTTP `409` while a presentation config, a credential config or the issuance configuration of the tenant still references the list. 9.x deleted the list anyway, and the presentation requests, wallet and key attestation checks and schema metadata publications that used it failed afterwards. The `409` body has `code: "TRUST_LIST_IN_USE"`, a `message` that names the configurations, and `references` with the `kind` of each and, for presentation and credential configs, its `id` and `description`; configurations the caller's roles cannot read are only counted. Configuration bundles and config folders imported in `replace` mode no longer delete such a list either: in 9.x their plan only stopped for a document of the bundle that named the list by `trustListId`. Now the plan item of the list is `blocked` with `TRUST_LIST_IN_USE` while any configuration that survives the import references it, also one outside the bundle or a reference by URL, so the import applies nothing; a startup import in `replace` mode skips the tenant and logs the issue ([details](../trust/trust-lists.md#delete-a-trust-list)).

**Do:** remove the references, or point them to another list, before you delete a list, through the API or by leaving the list out of a bundle or config folder. In scripts, treat `409` with `code: "TRUST_LIST_IN_USE"` as "still in use". If a `replace` import or `CONFIG_IMPORT_MODE=replace` stops with `TRUST_LIST_IN_USE`, keep the list in the bundle or folder, or remove the references it names, then plan again. Details: [Trust lists](../trust/trust-lists.md#delete-a-trust-list).

### Key chains: `DELETE` refuses key chains that configurations name

**Changed:** `DELETE /api/key-chain/{id}` answers HTTP `409` while a configuration of the tenant names the key chain: the `access` or `accessToken` entry of the tenant's key chain defaults (`key-chain-defaults.json`), `token.signingKeyId` of an authorization server of the issuance configuration, `keyChainId` of a credential configuration, a status list or a trust list, `accessKeyChainId` of a presentation configuration, or `issuerKeyChainId` or `revocationKeyChainId` of an internal trust list entity. 9.x deleted the key chain anyway: the configurations that named it failed to sign afterwards, and deleting the signing key chain of a trust list also deleted the trust list. A configuration that names no key chain and uses the tenant's default one does not count, except a trust list, which stores the key chain picked at creation. The `409` body has `code: "KEY_CHAIN_IN_USE"`, a `message` that names the configurations, and `references` with the `kind` of each and, except for the issuance configuration and the key chain defaults, its `id` and `description`; configurations the caller's roles cannot read are only counted. Configuration bundles and config folders imported in `replace` mode no longer delete such a key chain either: the plan item of the key chain is `blocked` with `KEY_CHAIN_IN_USE` while a configuration that survives the import names it, also one outside the bundle, so the import applies nothing; a startup import in `replace` mode skips the tenant and logs the issue ([details](../trust/keys-and-certificates.md#delete-a-key-chain)).

**Do:** point the configurations to another key chain, or remove the field so they use the default key chain, before you delete a key chain, through the API or by leaving the key chain out of a bundle or config folder. Delete a trust list before its signing key chain. In scripts, treat `409` with `code: "KEY_CHAIN_IN_USE"` as "still in use". If a `replace` import or `CONFIG_IMPORT_MODE=replace` stops with `KEY_CHAIN_IN_USE`, keep the key chain in the bundle or folder, or remove the references it names, then plan again. Details: [Keys and certificates](../trust/keys-and-certificates.md#delete-a-key-chain).

### Issuance notifications: the first event finishes the session

**Changed:** the first OpenID4VCI notification of an issuance session sets its status (`completed` or `failed`) and its `outcome`, `failureCode` and `errorReason`. Later notifications, for another credential of the offer or a repeated one, are still stored in `notifications`, sent to the webhook and answered as before, but no longer change the finished session. In 9.x the latest event decided, so for example `credential_accepted` after `credential_failure` turned a `failed` session into `completed` ([details](../reference/session-outcome.md#issuance-notifications)).

**Do:** if you derive a per-credential result from later events, read them from the notification webhook or from `notifications` of `GET /api/session/{id}` instead of the session status.

### Credential configurations: `constraints` accept only JSON Schema keywords

**Changed:** `POST /api/issuer/credentials` and the other writes of credential configurations answer HTTP `400` when a claim field's `constraints`, or a subschema in it, has a key that is not in the list under [Constraints](../issuance/claims.md#constraints), for example `format`, `$ref`, `nullable`, an `x-` extension or a form hint such as `widget`; the error names the field and the keyword. 9.x stored any key. In the Web Client, the offer form rendered formly's `widget.formlyConfig` from these keys, so a stored configuration could inject HTML and scripts into the page of everyone who opened the offer form for it.

10.0 ignores such keys in configurations stored by 9.x: claim validation at issuance, the offer form, schema metadata published to the registrar and exports leave them out. For most of them nothing changes, because since 9.0 issuance with them already failed (claims are validated with a strict JSON Schema validator that refuses unknown keywords such as `format`, `x-` extensions or `widget`). The validator did apply a few: `nullable`, `dependencies`, `$ref` with `$defs` or `definitions` and `$id`. A configuration that relies on them validates claims differently after the upgrade; for example, a claim with `nullable: true` no longer accepts `null`.

The generated API types of `@eudiplo/sdk-core` type `ClaimFieldDefinitionDto.constraints` as `ClaimConstraints` instead of an open object, and its `buildJsonSchema` and `deriveRuntimeArtifacts` leave out the other keys too.

**Do:** remove those keys from your credential configurations. Leave out a claim instead of sending `null`, write `dependencies` as `dependentRequired` or `dependentSchemas`, and put the subschema of a `$ref` in place. A configuration stored by 9.x is used without them, but sending its `fields` back through the API answers `400` until they are gone; files are covered under [Configuration files](#configuration-files).

## Configuration files

**Changed:** clients, KMS and registrar configurations and the key chain defaults have file format v2, credential configurations v3, tenants (`info.json`) and key chains v4 and issuance configurations v6:

- Credential configurations (`https://eudiplo.dev/schemas/v2/CredentialConfigFile.schema.json`) accept `x509` as `frameworkType` of `schemaMeta.trustedAuthorities` entries. Publishing schema metadata with an `x509` trusted authority and `credentialConfigId` writes such an entry; in 9.x the export of that credential configuration failed to import again. Format v3 (`https://eudiplo.dev/schemas/v3/CredentialConfigFile.schema.json`) accepts only JSON Schema validation and annotation keywords in `fields[].constraints` ([above](#credential-configurations-constraints-accept-only-json-schema-keywords)) and only claim patterns RE2 can run ([below](#credential-configurations-claim-patterns-must-suit-re2)).
- Key chains (`https://eudiplo.dev/schemas/v2/KeyChainConfigFile.schema.json`) accept `type` (`standalone` or `internalChain`), which `GET /api/key-chain/{id}/export` and configuration bundle exports now write. In 9.x the export of an internal chain without rotation was imported again as a standalone key chain that signed with the former root CA key. A 10.0 export of such a key chain carries `"type": "internalChain"` and is imported again as an internal chain with the same root CA certificate and a new signing key ([Keys and certificates](../trust/keys-and-certificates.md#import-a-key-and-certificate)); a 9.x export without `type` is still imported as before. Key chains with format v3 (`https://eudiplo.dev/schemas/v3/KeyChainConfigFile.schema.json`) also accept the usage type `federation` ([OpenID Federation](../trust/federation.md#publish-your-entity-configuration)), and format v4 (`https://eudiplo.dev/schemas/v4/KeyChainConfigFile.schema.json`) the usage type `accessToken` ([Access tokens](#access-tokens-signed-by-their-own-key-chain)). The new key chain format changes the hash stored for each applied key chain, so the first `upsert` or `replace` import after the upgrade applies every file-managed key chain once more, with new signing keys for CA keys.
- Clients (`https://eudiplo.dev/schemas/v2/ClientConfigFile.schema.json`) accept the new roles `audit:read`, `sessions:read`, `credentials:status` and `keys:manage` ([Credential status](#credential-status-issuanceoffer-no-longer-revokes-or-suspends)).
- KMS configurations (`https://eudiplo.dev/schemas/v2/KmsConfigFile.schema.json`) accept `algorithms` and `defaultAlgorithm` on providers ([Signing algorithms](../operate/kms.md#signing-algorithms)).
- Registrar configurations (`https://eudiplo.dev/schemas/v2/RegistrarConfigFile.schema.json`) accept `relyingPartyContact`, sent when EUDIPLO registers the relying party at the registrar ([Registrar](../trust/registrar.md#relying-party)).
- Tenants have format v4 (`https://eudiplo.dev/schemas/v4/TenantConfigFile.schema.json`), which adds no field to 9.x files. The new file `key-chain-defaults.json` (`https://eudiplo.dev/schemas/v1/KeyChainDefaultsConfigFile.schema.json`, resource `KeyChainDefaults/defaults`) holds the tenant's key chain per usage type; its `access` entry is the [default access key chain](../trust/keys-and-certificates.md#default-access-key-chain). Format v2 (`https://eudiplo.dev/schemas/v2/KeyChainDefaultsConfigFile.schema.json`) adds the `accessToken` entry ([Access token key chain](../trust/keys-and-certificates.md#access-token-key-chain)).
- Issuance configurations (`https://eudiplo.dev/schemas/v4/IssuanceConfigFile.schema.json`) accept `walletAttestationStatusCheckMode` on the configuration and its authorization servers ([Wallet and key attestation](../trust/attestation.md#2-require-wallet-attestation)). A v3 file is a valid v4 file. Format v5 (`https://eudiplo.dev/schemas/v5/IssuanceConfigFile.schema.json`) adds the entity configuration fields of `federation` ([OpenID Federation](../trust/federation.md#publish-your-entity-configuration)) and requires `federation.entityId` to be a URL ([below](#issuance-configuration-federationentityid-must-be-an-https-url)); any other v4 file is a valid v5 file. Format v6 (`https://eudiplo.dev/schemas/v6/IssuanceConfigFile.schema.json`) removes the top-level `signingKeyId`: the upgrade drops a set value with the warning `ISSUANCE_SIGNING_KEY_ID_REMOVED` and warns about every `token.signingKeyId` with `ACCESS_TOKEN_KEY_CHAIN_REQUIRED` ([below](#issuance-configuration-tokensigningkeyid-names-an-access-token-key-chain)).

10.0 imports files of older format versions and upgrades them unchanged; key chain files without `type` are imported as in 9.x. Three kinds of files change: issuance configurations lose a top-level `signingKeyId` with the warning `ISSUANCE_SIGNING_KEY_ID_REMOVED`, Tenant v2 and v3 files, which development builds of 10.0 wrote, lose their `defaultAccessKeyChainId` or `defaultKeyChains` with the warning `DEFAULT_KEY_CHAINS_MOVED` (set the value in `key-chain-defaults.json` instead), and credential configurations lose every key in `constraints` that v3 does not accept, each with the warning `CLAIM_CONSTRAINT_KEYWORD_REMOVED` at its path; a credential configuration with a claim pattern RE2 cannot run is not upgraded (`CLAIM_PATTERN_UNSUPPORTED`). Files and bundles exported from 10.0, including key chain exports, **cannot be imported into 9.x**.

**Do:**

- Update the CLI you use for `eudiplo config validate`, `config upgrade` and `config editor setup`, for example in CI, to 10.x; a 9.x CLI rejects v2 files and v4 issuance configurations.
- Rewrite configuration folders kept in Git once; otherwise `eudiplo config upgrade --check` reports every credential configuration below v3, every key chain below v4, every client and KMS configuration below v2 and every issuance configuration below v6 as `upgrade required`:

    ```bash
    eudiplo config upgrade ./config --dry-run   # show the changes
    eudiplo config upgrade ./config --output ./config-v10   # then replace ./config with it
    ```

- If a 9.x export contains a credential configuration with an `x509` trusted authority, export it again after the upgrade, or set its `$schema` to the v2 URL; as a v1 file it still fails validation.
- Before you import a 9.x export of an internal or external CA chain without rotation, export it again after the upgrade, or add `"type": "internalChain"` and, in a v1 document, set `$schema` to the v2 URL. Without `type`, its root CA key becomes the signing key. Add the field to such files in `CONFIG_FOLDER/<tenant>/key-chains/` before you start 10.0; in a bundle, `eudiplo config plan --diff` lists such a document with a `/spec/type` change from `internalChain` to `standalone` when the stored key chain is an internal chain. A key chain that was already imported that way has the root CA certificate as its active certificate (`GET /api/key-chain/{id}`, no `rootCertificate`); import the 9.x export again with `"type": "internalChain"` to restore it.
- `eudiplo config upgrade` drops unsupported `constraints` keys from v1 and v2 credential configurations. A v3 file with such keys fails validation; remove them, as `CLAIM_CONSTRAINT_KEYWORD_REMOVED` warnings or the validation errors list them. Exports from 10.0 leave them out.
- Keep a 9.x export from before the upgrade if you might need to restore 9.x.

See [Config bundle format](../reference/config-bundle-format.md#resource-types-and-versions).

### Issuance configuration: `token.signingKeyId` names an access token key chain

**Changed:** a bundle or config folder whose issuance configuration sets a `token.signingKeyId` that names no key chain with usage type `accessToken` is blocked with `KEY_CHAIN_USAGE_MISMATCH` (or `MISSING_RESOURCE_REFERENCE`), and a startup import then skips the tenant and logs the issue. A value the stored issuance configuration already has gets the same code as a warning, so an unchanged folder still imports; that authorization server's token requests fail until the value is fixed ([Access tokens](#access-tokens-signed-by-their-own-key-chain)). `eudiplo config upgrade` reports such values with the warning `ACCESS_TOKEN_KEY_CHAIN_REQUIRED` and drops a top-level `signingKeyId` with `ISSUANCE_SIGNING_KEY_ID_REMOVED`.

**Do:** before the first start of 10.0, remove `token.signingKeyId` from `issuance/issuance.json`, or point it to a key chain file with `"usageType": "accessToken"`.

### Issuance configuration: `federation.entityId` must be an https URL

**Changed:** `federation.entityId` is the entity identifier of the tenant in an OpenID Federation and, from 10.0, also `iss` and `sub` of its published entity configuration and the `openid_federation:` client identifier. When set, it must be an `https` URL with a host and without query, fragment, credentials or whitespace (OpenID Federation 1.0 Section 1.2); `http` is accepted only with `OUTBOUND_URL_ALLOW_HTTP=true`. An empty value still means "not set". 9.x accepted any string. An `issuance.json` with another value fails its import on every start. A configuration bundle or document with one fails its plan, except an `http` value without `OUTBOUND_URL_ALLOW_HTTP=true`, which passes the plan and fails when it is applied. `eudiplo config upgrade` stops with the required input `FEDERATION_ENTITY_ID_INVALID` and writes nothing until the value is fixed; `eudiplo config validate` gives a v4 document the full check except `OUTBOUND_URL_ALLOW_HTTP`; for `issuance.json` files and v5 documents it only rejects values that are no `http(s)` URL or have a query, fragment or whitespace. A value stored by 9.x stays in the database until `federation.entityId` is replaced; a save that sends it back, as the Web Client does, answers `400`. Meanwhile issuer metadata keeps using it, federation SD-JWT VCs fall back to `x5c`, the entity configuration endpoint answers `404` and `openid_federation` presentation requests answer `400`.

**Do:** set `federation.entityId` to `<PUBLIC_URL>/issuers/<tenant>`, the URL your entity is registered under with its trust anchor, in `issuance.json`, bundles and stored configurations (**Issuer Settings** in the Web Client).

### `registrar.json` and bundles: URL rule and policy check on import

**Changed:** a `registrar.json` whose `registrarUrl` or `oidcUrl` has a query, a fragment or credentials makes the import plan of its tenant fail, so no configuration file of that tenant is applied on any start until the file is fixed; the tenant itself is still created or updated from `info.json`, unless its settings are [detached or changed through the API](../operate/configuration-as-code.md#configuration-model). A new or changed `registrar.json`, and a `RegistrarConfig` in a configuration bundle imported through `POST /api/config-bundles/import` or `/import/archive`, is now checked against the outbound URL policy, without resolving its hosts: the scheme, the allowlist, reserved names and IP addresses. If a URL is blocked, the import of that tenant stops at the registrar configuration with `CONFIG_APPLY_FAILED`; a host that does not resolve yet does not stop it, and the address is checked when EUDIPLO first uses it. The credentials are no longer checked on import (see below). `eudiplo config validate` does not check the URL rule.

**Do:** before upgrading, remove any query, fragment or credentials from the URLs in `registrar.json`, and allow the registrar in the outbound URL policy as described under [Operators](#registrar-requests-follow-the-outbound-url-policy).

### Registrar: imports remove omitted optional fields and skip the credential check

**Changed:** in 9.x, a configuration bundle and `CONFIG_FOLDER/<tenant>/registrar.json` kept a stored `clientSecret` and `registrationCertificateDefaults` that the document left out. The import also checked the credentials against the registrar: when the registrar was unreachable, the tenant's import stopped at the registrar configuration, and the resources after it were not applied. In `upsert` and `replace` mode, 10.0 removes an omitted `clientSecret` and `registrationCertificateDefaults`, and the plan lists their removal (`eudiplo config plan --diff`, or `changes` in the answer of `POST /api/config-bundles/plan`; the client secret is redacted). It saves the configuration without contacting the registrar; wrong credentials fail when EUDIPLO first uses them. An export of a registrar configuration without client secret no longer contains a `clientSecret` placeholder and its `SECRET_REQUIRED` requirement.

**Do:** add `registrationCertificateDefaults`, and `clientSecret` if the registrar needs one, to every bundle and `registrar.json` that should keep them. Bundles exported by 9.x from a registrar account without client secret contain a `clientSecret` placeholder; remove it before you import them. Check the credentials before you import them: an import no longer rejects wrong ones, they fail with `400` when EUDIPLO first uses them, for example when you request an access certificate. Details: [Registrar](../trust/registrar.md#1-connect-the-registrar).

### Clients: another secret ends the client's tokens

**Changed:** a `Client` document or a file in `CONFIG_FOLDER/<tenant>/clients/` that gives an existing client another secret, or `!generate` in a bundle, ends the tokens issued with the old secret ([Deleting a client or changing its secret ends its access](#deleting-a-client-or-changing-its-secret-ends-its-access-jwt_expires_in-removed)). A client file without `secret` gets a new random secret at every start in `upsert` or `replace` mode, so its tokens now end at every restart; 9.x kept them for up to 24 hours. The same secret as stored keeps the tokens.

**Do:** set `secret` in every client file that an integration uses with `CONFIG_IMPORT_MODE=upsert` or `replace`.

### Key chains: imports remove an omitted description and rotation settings

**Changed:** a `KeyChain` document replaces the stored key chain, and the plan already listed a description it left out as removed, but with a `private-jwk` or `external-reference` key source 9.x kept the stored description. In `upsert` and `replace` mode, 10.0 removes an omitted `description`, as the plan lists. The plan now also lists the rotation policy as the import stores it: without `rotationPolicy` rotation is disabled, `null` in `intervalDays` or `certValidityDays` means the same as leaving it out, and a private key without `activeJwk` gets the import defaults of 90 and 365 days when rotation is enabled. A key chain of an external KMS exported without rotation interval therefore plans as `unchanged` instead of `update`. 10.0 exports leave unset rotation values out instead of writing `null`.

A key chain whose document has not changed since it was last applied keeps its stored description and rotation settings until the document changes ([Key chains: an unchanged document is not applied again](#key-chains-an-unchanged-document-is-not-applied-again)).

**Do:** add `description` to every key chain in a bundle or in `CONFIG_FOLDER/<tenant>/key-chains/` that should keep it. Details: [Config bundle format](../reference/config-bundle-format.md#import-modes-and-plan-actions).

### Key chains: an unchanged document is not applied again

**Changed:** in `upsert` and `replace` mode, 9.x planned a key chain with a private key or `regenerate` as `update` on every import, because the stored keys never equal the document, and applied it again: a CA key got a new signing key, a rotation since the import was undone, `regenerate` created new key material, and certificates EUDIPLO creates during an import were issued again. With `CONFIG_IMPORT_MODE=upsert` or `replace`, this happened at every startup. In 10.0, a `KeyChain` document that is identical to the one last applied from the same source plans `unchanged` while the key chain is `file-managed`, also when 9.x applied it, and the key chain stays as it is. A changed document is compared and applied as before, and reattaching always applies the folder version. So certificates EUDIPLO created during the import are no longer renewed at each start, for example the self-signed certificate of a key without `crt` (valid 365 days), the signing certificate of a CA key and the certificate of a `regenerate` key chain (valid `certValidityDays`). A changed `PUBLIC_URL` or tenant name reaches them only at the next rotation or re-import.

**Do:**

- Renew every certificate EUDIPLO created during an import before it expires. For a key chain with rotation, set an `intervalDays` below its `certValidityDays`; the demo configuration now rotates its attestation and status list keys every 20 days. For a `private-jwk` key without `crt` and without rotation, raise `metadata.generation` to get a new self-signed certificate for the same key, or supply your own `crt`; enabling rotation there would make the key the CA of a new signing key ([key chain types](../trust/keys-and-certificates.md#key-chain-types)). `POST /api/key-chain/{id}/rotate` renews a certificate with a new key.
- To apply an unchanged key chain document again, for example a bundle with `regenerate` that you import to create new key material, raise `metadata.generation` in the document; in a bundle, also update the document's `sha256` in `manifest.json`. Details: [Config bundle format](../reference/config-bundle-format.md#import-modes-and-plan-actions).

### Key chains: bundles leave out the encryption key chain

**Changed:** 9.x exports contained the tenant's encryption key chain as a `KeyChain` document with `usageType: "encrypt"` and the requirement `PRIVATE_KEY_REQUIRED`; supplying a key or `regenerate` replaced the tenant's decryption key. 10.0 exports leave it out, and imports neither change nor delete it. A plan skips a `KeyChain` document with the ID of the tenant's encryption key chain and warns with `KEY_CHAIN_ID_RESERVED`, in every mode and in the startup import of `CONFIG_FOLDER/<tenant>/key-chains/`.

**Do:** nothing for a 9.x export imported into the tenant it came from. Before you import it into another tenant, remove that document: there it would ask for a private key and create a key chain that EUDIPLO never uses. The same applies to 10.0 exports of a tenant whose encryption key chain a 9.x import replaced (see the encryption key chain section under Integrators): they still contain it. Details: [Config bundle format](../reference/config-bundle-format.md#import-modes-and-plan-actions).

### Clients: an unchanged `!generate` document keeps its secret

**Changed:** in `upsert` and `replace` mode, 9.x planned a `Client` document with `"secret": "!generate"` as `update` on every import and gave the client a new secret each time, returned in `generatedSecrets`; a startup import with `CONFIG_IMPORT_MODE=upsert` or `replace` did so at every start without showing it, so the client could no longer authenticate after a restart. In 10.0, such a document that is identical to the one last applied from the same source plans `unchanged` while the client is `file-managed`, also when 9.x applied it, and the client keeps its secret. With Keycloak (`OIDC` set), such a client is still applied on every import, which undoes changes made in Keycloak, but it keeps its secret. A changed document, another source or reattaching generates a new secret as before.

**Do:** to get a new secret from an unchanged document, raise `metadata.generation`; in a bundle, also update the document's `sha256` in `manifest.json`. A startup import still does not show the secret it generates; it logs a warning naming the client. To get the secret of such a client, apply it with **Apply from file** under **Settings > Config Portability** or reattach it ([clients with generated secrets](../operate/configuration-as-code.md#clients-with-generated-secrets)). Details: [Config bundle format](../reference/config-bundle-format.md#import-modes-and-plan-actions).

### Credential configurations: claim patterns must suit RE2

**Changed:** a credential configuration in `credentials/*.json` or in a bundle or document whose claim pattern RE2 cannot run (see [under Integrators](#credential-configurations-claim-patterns-run-on-re2)) fails its import plan, so no configuration file of that tenant is applied on any start until the file is fixed. `eudiplo config upgrade` stops at such a pattern in a v1 or v2 file with the required input `CLAIM_PATTERN_UNSUPPORTED` at its path and writes nothing until it is rewritten; `eudiplo config validate` reports it the same way for v1 and v2 documents, but does not check patterns in v3 files or files without `$schema`. A 10.0 export of a configuration stored by 9.x keeps such a pattern, so importing it again is blocked as well.

**Do:** before upgrading, rewrite such patterns in your configuration files and exports.
