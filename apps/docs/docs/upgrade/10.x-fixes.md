# Fixes in 10.x that change behavior

A few fixes released within 10.x close a security or conformance gap and thereby change what EUDIPLO accepts or issues. Each section below says what changed and what to do; skip the sections that do not apply to you. The [release notes](https://github.com/EUDIPLO/eudiplo/releases) say which release carries each fix.

## Before you upgrade

- Check that `meta.vct_values` and `meta.doctype_value` of your presentation configurations name the exact `vct` and docType of the credentials you accept: credentials of another type are now rejected ([Presentations](#presentations-credentials-must-be-of-a-requested-type)).
- If you use the demo `pid` presentation configuration from before this fix, update its `vct_values` ([Presentations](#presentations-credentials-must-be-of-a-requested-type)).
- If you verify credentials, check that the CA certificates of their issuers' chains, and of their status list signers' chains, carry `basicConstraints` `cA` TRUE, and that no certificate marks an extension critical that EUDIPLO does not process, such as `nameConstraints`: such credentials are now rejected ([Presentations: certificate paths](#presentations-certificate-paths-must-meet-rfc-5280-constraints)). This includes credentials you issue yourself under a certificate from your own PKI.
- Follow the [upgrade procedure](./index.md#upgrade-procedure).

## Operators

### Presentations: credentials must be of a requested type

**Changed:** a presented SD-JWT VC whose `vct` is not one of the credential query's `meta.vct_values`, or an mDOC whose docType is not its `meta.doctype_value`, fails with `credential_type_mismatch`, HTTP 400 to the wallet and session `failed` ([OpenID4VP 1.0, Section 8.6](https://openid.net/specs/openid-4-verifiable-presentations-1_0.html#section-8.6)). This applies to OpenID4VP flows, also over the Digital Credentials API, and to ISO 18013-7 flows. The values are compared as exact strings; in OpenID4VP flows `<TENANT_URL>` is resolved first. An SD-JWT VC whose type only `extends` one of `vct_values` is rejected too, because EUDIPLO does not resolve type metadata. Earlier 10.x releases accepted a credential of any type once its signature, issuer and claims checked out, so a wallet could answer a PID query with another credential of a trusted issuer.

The demo configuration's `pid` presentation now requests `urn:eudi:pid:de:1`, the `vct` of the demo PID. It requested `<TENANT_URL>/credentials-metadata/vct/pid`, which no demo credential carries.

**Do:** check that `vct_values` and `doctype_value` of every presentation configuration list the exact types your issuers put in their credentials, including every type that extends one you accept, for example `["urn:eudi:pid:1", "urn:eudi:pid:de:1"]`. If presentations fail with `credential_type_mismatch`, compare the message, which names the accepted types, with the `vct` or docType of the credentials wallets hold. If you imported the demo configuration or created a project with `eudiplo init` before this fix was released, your stored `pid` presentation configuration still requests `<TENANT_URL>/credentials-metadata/vct/pid` and rejects the demo PID: set its `vct_values` to `["urn:eudi:pid:de:1"]`, or import the current demo file again. Details: [Credential type](../presentation/dcql.md#credential-type).

### Presentations: certificate paths must meet RFC 5280 constraints

**Changed:** a presented SD-JWT VC or mDOC is rejected with `no_trust_chain_to_root`, HTTP 400 to the wallet and session `failed`, when the certificate path from its signing certificate up to the certificate the trust list lists breaks an RFC 5280 constraint: a certificate that issues the one below it must be a CA (`basicConstraints` `cA` TRUE, `keyCertSign`, `pathLenConstraint`), and no certificate may mark an extension critical that EUDIPLO does not process, such as `nameConstraints`. This includes the certificate the trust list lists, when it issued the one below it, and version 1 or 2 CA certificates, which carry no `basicConstraints`. Wallets get HTTP 400 for such credentials. The same applies to the path of its status list or identifier list: an SD-JWT VC then fails with `Status List JWT verification failed`, an mDOC with `no_trust_chain_to_root`, also with `statusCheckMode: best_effort`. Without a trust list (`SKIP_TRUST_AUTHORITY=true`), an mDOC's presented chain is checked in the same way. Earlier 10.x releases checked only signatures, validity periods and the match with the trust list: any end-entity key of a listed provider could issue further signing certificates, and a critical extension with a restriction EUDIPLO does not enforce was ignored. The certificates of ISO/IEC 18013-5 Annex B and those EUDIPLO creates for its key chains meet the constraints. Wallet and key attestations are unchanged.

**Do:** nothing for issuers whose CA certificates carry `basicConstraints` `cA` TRUE and mark only the extensions listed in [Certificate path constraints](../trust/trust-lists.md#certificate-path-constraints) critical. If presentations fail with `no_trust_chain_to_root` and the server log says `Certificate path constraint: ...`, ask the issuer, or for a status list its signer, for a certificate chain that meets the constraints; the message names the certificate and the constraint. If you issue under a key chain imported from your own PKI, check its certificates the same way. Details: [Certificate path constraints](../trust/trust-lists.md#certificate-path-constraints).

## Wallet-facing behavior

### Presentations: a credential of another type is refused

**Changed:** a wallet that answers a credential query with a credential of a type its `meta` does not name gets HTTP 400: in OpenID4VP flows the `Incomplete Presentation` error body described in [What the wallet or browser receives](../reference/session-outcome.md#what-the-wallet-or-browser-receives), in ISO 18013-7 flows `{"error": "credential_type_mismatch", "message": "..."}`. With a configured redirect, the redirect carries `error=invalid_request` and the message as `error_description`.

This includes an SD-JWT VC whose `vct` only extends a listed one, which OpenID4VP 1.0 Appendix B.3.5 lets a wallet return: EUDIPLO does not follow type inheritance.

**Do:** wallets that present only credentials whose `vct` or docType the query lists need no change.
