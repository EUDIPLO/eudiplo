# Fixes in 10.x that change behavior

A few fixes released within 10.x close a security or conformance gap and thereby change what EUDIPLO accepts or issues. Each section below says what changed and what to do; skip the sections that do not apply to you. The [release notes](https://github.com/EUDIPLO/eudiplo/releases) say which release carries each fix.

## Before you upgrade

- Check that `meta.vct_values` and `meta.doctype_value` of your presentation configurations name the exact `vct` and docType of the credentials you accept: credentials of another type are now rejected ([Presentations](#presentations-credentials-must-be-of-a-requested-type)).
- If you use the demo `pid` presentation configuration from before this fix, update its `vct_values` ([Presentations](#presentations-credentials-must-be-of-a-requested-type)).
- If you verify credentials, check that the CA certificates of their issuers' chains, and of their status list signers' chains, carry `basicConstraints` `cA` TRUE, and that no certificate marks an extension critical that EUDIPLO does not process, such as `nameConstraints`: such credentials are now rejected ([Presentations: certificate paths](#presentations-certificate-paths-must-meet-rfc-5280-constraints)). This includes credentials you issue yourself under a certificate from your own PKI.
- If you verify mDOCs, expect a presentation in which a CBOR map repeats a key, such as a COSE header that names `alg` twice, to be rejected ([Presentations: repeated map keys](#presentations-an-mdoc-whose-cbor-repeats-a-map-key-is-refused)).
- If you accept wallet or key attestations in the TS3 1.5 format (EUDI Wallet), check that every wallet provider serves the status lists their `client_status` and `key_storage_status` name and signs them as its other status lists: they are now checked ([Wallet and key attestations](#wallet-and-key-attestations-ts3-15-status-claims-are-checked)).
- If credential configurations set `revokeWithWalletUnit`, expect their credentials to be revoked also when the wallet attestation (WIA) presented at the token endpoint is revoked ([Revocation with the wallet unit](#revocation-with-the-wallet-unit-the-wallet-attestation-is-followed-too)).
- If credential configurations set `revokeWithWalletUnit` and your wallets present TS3 1.5 attestations, expect shorter credential lifetimes and refused requests for attestations whose status maintenance period has ended ([Credential expiry](#credential-expiry-bounded-by-the-status-maintenance-period)).
- If a tenant `kms.json` (`<CONFIG_FOLDER>/<tenant-id>/kms.json`) contains `${VAR}` placeholders, list the variables you wrote there in `KMS_TENANT_VARIABLES`, replace a placeholder in `defaultProvider` or the `id` of a provider with the variable's value, and check every placeholder you did not write ([Configuration files](#configuration-files-placeholders-are-limited-to-the-variables-a-file-may-use)).
- If a configuration file names a variable that configures EUDIPLO itself, such as `${MASTER_SECRET}` or `${DB_PASSWORD}`, or a tenant file names `${VAULT_ADDR}`, `${VAULT_TOKEN}` or `${AWS_REGION}`, set a variable of your own to that value and name it instead ([Configuration files](#configuration-files-placeholders-are-limited-to-the-variables-a-file-may-use)).
- If a file of a tenant folder other than `kms.json` names `${AWS_ACCESS_KEY_ID}`, `${AWS_SECRET_ACCESS_KEY}`, `${AWS_SESSION_TOKEN}`, `${AWS_CONTAINER_AUTHORIZATION_TOKEN}`, `${AZURE_CLIENT_SECRET}`, `${AZURE_CLIENT_CERTIFICATE_PASSWORD}` or `${AZURE_PASSWORD}`, set a variable of your own to that value and name it instead ([Configuration files](#configuration-files-placeholders-are-limited-to-the-variables-a-file-may-use)).
- If you placed exports of tenants in `CONFIG_FOLDER` with an earlier release, search those tenant folders for `${` and check every placeholder you did not write ([Exports](#exports-placeholder-text-is-written-in-an-escaped-form)).
- If a file of a tenant folder contains `$${`, it now stands for the text `${` and no longer for a `$` followed by a placeholder ([Exports](#exports-placeholder-text-is-written-in-an-escaped-form)).
- CLI users: upgrade the CLI and the backend together. Their handling of `$${` differs from earlier releases, also between two patch releases ([Exports](#exports-placeholder-text-is-written-in-an-escaped-form)).
- Integrators and CLI users: a configuration bundle you send to the API, also with `eudiplo config plan` and `eudiplo config import`, now stores `$${` as the text `${`, and its plan warns about a `${VAR}` inside a longer value ([Exports](#exports-placeholder-text-is-written-in-an-escaped-form)).
- Integrators and CLI users: if a client sends `${VAR}` placeholders to `PUT /api/key-chain/providers/config` or in the `KmsConfig` document of a configuration bundle, also with `eudiplo config import`, send the values, or write the placeholders to the tenant's `kms.json` file ([Configuration files](#configuration-files-placeholders-are-limited-to-the-variables-a-file-may-use)).
- If a tenant `kms.json` holds a `pkcs11` provider or an `http` provider with `mtls` authentication, list its files in `KMS_TENANT_FILES`; if it holds an `aws-kms` provider without `accessKeyId` and `secretAccessKey`, give it credentials, move it to the global `kms.json` or set `KMS_TENANT_AWS_DEFAULT_CREDENTIALS=true`. Check every such provider you did not write ([Tenant KMS configuration](#tenant-kms-configuration-host-files-and-the-instances-aws-identity-need-the-operator)).
- If a `kms.json` sets `keysPath`, `healthPath` or `apiPath`, check that each is a path such as `/v1/keys`, and that mTLS files are regular files of at most 1 MiB ([Tenant KMS configuration](#tenant-kms-configuration-host-files-and-the-instances-aws-identity-need-the-operator)).
- If a tenant `kms.json` holds a `vault`, `http` or `csc` provider whose server is on HTTP or on a private or loopback address, move the provider to the global `kms.json` or set `OUTBOUND_URL_ALLOW_HTTP` and `OUTBOUND_URL_ALLOW_PRIVATE_NETWORK`; if `OUTBOUND_URL_ALLOWED_HOSTS` is set, add the hosts of tenant KMS servers to it ([Tenant KMS configuration](#tenant-kms-configuration-host-files-and-the-instances-aws-identity-need-the-operator)).
- Integrators and CLI users: if a client sends a `pkcs11` provider, mTLS files or an `aws-kms` provider without credentials to `PUT /api/key-chain/providers/config` or in the `KmsConfig` document of a configuration bundle, have the operator write the provider to the tenant's `kms.json` file and, for `aws-kms` without credentials, set `KMS_TENANT_AWS_DEFAULT_CREDENTIALS=true` ([Tenant KMS configuration](#tenant-kms-configuration-host-files-and-the-instances-aws-identity-need-the-operator)).
- Integrators and CLI users: if a client imports `KeyChain` documents with an `external-reference` key source for keys the tenant does not hold yet, on a KMS provider that tenants share, have the operator put these key chain files into the tenant's configuration folder ([Key chains](#key-chains-keys-of-a-shared-kms-provider-stay-with-their-tenant)).
- Integrators: `PUT` and `DELETE /api/key-chain/providers/config` can answer `409` while key chains use a provider of the tenant's own `kms.json`; delete those key chains first ([Key chains](#key-chains-keys-of-a-shared-kms-provider-stay-with-their-tenant)).
- If you look up keys in a shared Vault or HTTP KMS by the `kid` they were imported with through the API, use the `kid` the key chain shows: new imports get a name EUDIPLO chooses ([Key chains](#key-chains-keys-of-a-shared-kms-provider-stay-with-their-tenant)).
- Integrators: `POST /api/key-chain/import` without an `id` can answer `409` (`CONFIG_WRITER_ACTIVE`) while another configuration change of the tenant runs; send a tenant's imports one after the other and retry on `409` ([Key chains](#key-chains-keys-of-a-shared-kms-provider-stay-with-their-tenant)).
- If you run several backend replicas and tenants have their own `kms.json`, mount the same writable `CONFIG_FOLDER` into all replicas. A tenant `kms.json` you edit by hand now applies at the tenant's next key operation without a restart, so replace it by renaming a temporary file ([Key chains](#key-chains-keys-of-a-shared-kms-provider-stay-with-their-tenant)).
- If a `StatusList` document or status list configuration file for a new list sets `capacity` above 1,000,000, or a tenant's status list default does, lower it: such a list is no longer created ([Status lists](#status-lists-capacity-is-limited-to-1000000-on-every-path)).
- With Keycloak: if you rotate client secrets through `POST /api/client/<id>/rotate-secret`, note that it now answers `404` for clients EUDIPLO does not manage for a tenant, including `OIDC_CLIENT_ID` and `AUTH_CLIENT_ID` ([Clients](#clients-with-keycloak-only-clients-eudiplo-manages-for-a-tenant-have-their-secret-rotated)).
- If mDOC credential configurations have top-level fields without `namespace` and with a one-segment `path`, expect their claim paths in the issuer metadata to start with the document type's namespace, and default values of their children to be issued in that namespace ([Issuance](#issuance-every-mdoc-claim-path-names-a-namespace)).
- Follow the [upgrade procedure](./index.md#upgrade-procedure).

## Operators

### Presentations: credentials must be of a requested type

**Changed:** a presented SD-JWT VC whose `vct` is not one of the credential query's `meta.vct_values`, or an mDOC whose docType is not its `meta.doctype_value`, fails with `credential_type_mismatch`, HTTP 400 to the wallet and session `failed` ([OpenID4VP 1.0, Section 8.6](https://openid.net/specs/openid-4-verifiable-presentations-1_0.html#section-8.6)). This applies to OpenID4VP flows, also over the Digital Credentials API, and to ISO 18013-7 flows. The values are compared as exact strings; in OpenID4VP flows `<TENANT_URL>` is resolved first. An SD-JWT VC whose type only `extends` one of `vct_values` is rejected too, because EUDIPLO does not resolve type metadata. Earlier 10.x releases accepted a credential of any type once its signature, issuer and claims checked out, so a wallet could answer a PID query with another credential of a trusted issuer.

The demo configuration's `pid` presentation now requests `urn:eudi:pid:de:1`, the `vct` of the demo PID. It requested `<TENANT_URL>/credentials-metadata/vct/pid`, which no demo credential carries.

**Do:** check that `vct_values` and `doctype_value` of every presentation configuration list the exact types your issuers put in their credentials, including every type that extends one you accept, for example `["urn:eudi:pid:1", "urn:eudi:pid:de:1"]`. If presentations fail with `credential_type_mismatch`, compare the message, which names the accepted types, with the `vct` or docType of the credentials wallets hold. If you imported the demo configuration or created a project with `eudiplo init` before this fix was released, your stored `pid` presentation configuration still requests `<TENANT_URL>/credentials-metadata/vct/pid` and rejects the demo PID: set its `vct_values` to `["urn:eudi:pid:de:1"]`, or import the current demo file again. Details: [Credential type](../presentation/dcql.md#credential-type).

### Presentations: certificate paths must meet RFC 5280 constraints

**Changed:** a presented SD-JWT VC or mDOC is rejected with `no_trust_chain_to_root`, HTTP 400 to the wallet and session `failed`, when the certificate path from its signing certificate up to the certificate the trust list lists breaks an RFC 5280 constraint: a certificate that issues the one below it must be a CA (`basicConstraints` `cA` TRUE, `keyCertSign`, `pathLenConstraint`), and no certificate may mark an extension critical that EUDIPLO does not process, such as `nameConstraints`. This includes the certificate the trust list lists, when it issued the one below it, and version 1 or 2 CA certificates, which carry no `basicConstraints`. Wallets get HTTP 400 for such credentials. The same applies to the path of its status list or identifier list: an SD-JWT VC then fails with `Status List JWT verification failed`, an mDOC with `no_trust_chain_to_root`, also with `statusCheckMode: best_effort`. Without a trust list (`SKIP_TRUST_AUTHORITY=true`), an mDOC's presented chain is checked in the same way. Earlier 10.x releases checked only signatures, validity periods and the match with the trust list: any end-entity key of a listed provider could issue further signing certificates, and a critical extension with a restriction EUDIPLO does not enforce was ignored. The certificates of ISO/IEC 18013-5 Annex B and those EUDIPLO creates for its key chains meet the constraints. Wallet and key attestations are unchanged.

**Do:** nothing for issuers whose CA certificates carry `basicConstraints` `cA` TRUE and mark only the extensions listed in [Certificate path constraints](../trust/trust-lists.md#certificate-path-constraints) critical. If presentations fail with `no_trust_chain_to_root` and the server log says `Certificate path constraint: ...`, ask the issuer, or for a status list its signer, for a certificate chain that meets the constraints; the message names the certificate and the constraint. If you issue under a key chain imported from your own PKI, check its certificates the same way. Details: [Certificate path constraints](../trust/trust-lists.md#certificate-path-constraints).

### Presentations: an mDOC whose CBOR repeats a map key is refused

**Changed:** a presented mDOC in which a CBOR map repeats a key fails with `verification_error`, HTTP 400 to the wallet and session `failed`. This covers every map of the DeviceResponse, including the data elements, the protected and unprotected headers of `IssuerAuth` and of the device signature or MAC, and the Mobile Security Object. For a COSE header, [RFC 9052, Section 3](https://www.rfc-editor.org/rfc/rfc9052.html#section-3) requires it: a message whose header map repeats a label must be rejected as malformed. An integer, float, text or byte string key counts as repeated by its value, so the label `1` in a longer integer encoding or as the float `1.0` repeats `1`. The same check refuses a DeviceResponse that it cannot read: bytes that are not well-formed CBOR, including text that is not UTF-8, nesting deeper than 128 levels, and a map key that is an array, a map or a tagged value of more than 1,024 bytes. Earlier 10.x releases kept the last entry of such a map and dropped the others, so they accepted, for example, an `IssuerAuth` whose protected header names `alg` twice. This applies to OpenID4VP flows, also over the Digital Credentials API, and to ISO 18013-7 flows. The status lists and identifier lists an mDOC names are not checked this way.

**Do:** nothing for credentials and wallets that encode each map key once, as CBOR requires ([RFC 8949, Section 5.6](https://www.rfc-editor.org/rfc/rfc8949.html#section-5.6)). If presentations fail with `verification_error` and the server log says `mDOC verification failed: Error: ... repeats the map key ...`, `... is not well-formed CBOR`, `... is nested too deeply` or `... has a map key of more than 1024 bytes`, the message names the structure and the key. Ask the issuer for `IssuerAuth protected header`, `IssuerAuth payload` (the Mobile Security Object) and a repeated data element in `DeviceResponse`, and the wallet provider for the others, such as `DeviceSignature protected header` or `DeviceMac protected header`.

### Wallet and key attestations: TS3 1.5 status claims are checked

**Changed:** EUDIPLO reads the status list entry of a wallet attestation from `client_status.status` and of a key attestation from `key_storage_status.status`, the claims of TS3 (EUDI Wallet Unit Attestations) 1.5 and later, in addition to the top-level `status` claim of OpenID4VCI 1.0 and TS3 1.4.1. Earlier 10.x releases ignored the TS3 claims, so it accepted attestations of revoked wallet instances and key storages and never fetched their lists. With `walletAttestationStatusCheckMode` `strict` or `best_effort` (the default), such an attestation is now rejected as one with a top-level `status` is: when its entry is revoked or suspended, when its list cannot be read, is not the named list or is not signed by the provider, and when the claim is malformed (`client_status` or `key_storage_status` not a JSON object, a malformed `status` in it, or an `exp` in it that is not a non-negative number). `strict` also rejects it when the list cannot be fetched. An attestation that carries both claims has both entries checked. The PAR and token endpoints (including the refresh grant) answer as for a top-level `status` claim, the credential endpoint `invalid_proof`. With `revokeWithWalletUnit`, a credential issued for a TS3 1.5 key attestation now follows its `key_storage_status` entry ([Which claim names the status](../trust/attestation.md#which-claim-names-the-status)); credentials issued by 10.x keep following the entry recorded then.

**Do:** before you upgrade, check with your wallet providers that the lists their TS3 attestations name are served and signed as their other status lists: under the revocation certificate your wallet-provider trust lists name for the provider, or its attestation certificate if they name none. To accept attestations while a list is unreachable, keep `best_effort`; `disabled` skips the check.

### Revocation with the wallet unit: the wallet attestation is followed too

**Changed:** with `revokeWithWalletUnit: true`, EUDIPLO records the status list entry of the wallet attestation (`client_status.status`, else `status`) that the `built-in` authorization server accepted at its token endpoint, next to that of the key attestation, with every credential issued with the access token. The background check (`WALLET_UNIT_STATUS_CHECK_INTERVAL`) revokes the credential when either entry is revoked and sends the same `wallet_unit_revoked` webhook. Earlier 10.x releases followed the key attestation only, so a revoked wallet instance kept its credentials (TS3 1.5 section 2.4.3). Credentials issued by 10.x keep following only the key attestation recorded then. A database migration adds `session.walletInstanceStatus` and makes `attestationKind` part of the primary key of `credential_wallet_unit`; existing records become `key` records.

**Do:** nothing for the configuration. If you turned on `revokeWithWalletUnit` and your wallets present wallet attestations, make sure the wallet provider's status list for wallet instances is served and signed as its key attestation list is; while it cannot be read, nothing is revoked and the reason is logged. The check matches the provider in the issuance configuration's `walletProviderTrustLists`: if the built-in authorization server has its own lists, add the wallet providers to the issuance configuration's lists as well.

### Credential expiry: bounded by the status maintenance period

**Changed:** with `revokeWithWalletUnit: true`, a credential now expires one second before the earlier of `client_status.exp` (wallet attestation accepted by the built-in authorization server) and `key_storage_status.exp` (key attestation of the proof), when that is before the expiry `lifeTime` gives (TS3 1.5 section 2.4.3). An SD-JWT VC without `lifeTime` then gets an `exp`. When the period has already ended, the credential endpoint refuses the request with `credential_request_denied`, deferred requests included; a deferred transaction whose period ends while it is pending is marked failed by `POST /api/issuer/deferred/{transactionId}/complete`, which then returns it with status `failed`. Earlier 10.x releases ignored these values, so its credentials could outlive the period in which the wallet provider keeps the wallet unit's status. Sessions and deferred transactions created by earlier 10.x releases carry no maintenance period, so credentials issued from them after the upgrade are not bounded. The expiry of configurations without `revokeWithWalletUnit` is unchanged; a malformed `client_status.exp` or `key_storage_status.exp` rejects the attestation for every configuration ([above](#wallet-and-key-attestations-ts3-15-status-claims-are-checked)).

**Do:** check with your wallet providers that their attestations' maintenance periods are at least as long as your credentials' `lifeTime` (TS3 1.5 guarantees 31 days), or accept shorter credentials. EUDIPLO does not publish `preferred_client_status_period` or `preferred_key_storage_status_period`.

### Configuration files: placeholders are limited to the variables a file may use

**Changed:** a `${VAR}` placeholder resolves only a variable the file may use ([variables a file can use](../reference/config-bundle-format.md#variables-a-file-can-use)):

- A tenant `kms.json` resolves your own variables only if the new setting `KMS_TENANT_VARIABLES` (comma-separated names, empty by default) lists them. This applies to every stored tenant `kms.json`.
- A tenant `kms.json` cannot contain a placeholder in `defaultProvider` or in the `id` of a provider, also not for a listed variable.
- No configuration file resolves a variable that configures EUDIPLO itself ([environment variables](../reference/environment-variables.md)), such as `MASTER_SECRET`, `AUTH_CLIENT_SECRET` or `DB_PASSWORD`. Exceptions: `PUBLIC_URL` resolves in every file, and `VAULT_ADDR`, `VAULT_TOKEN` and `AWS_REGION` in the global `kms.json`.
- A file of a tenant folder other than `kms.json` does not resolve `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_CONTAINER_AUTHORIZATION_TOKEN`, `AZURE_CLIENT_SECRET`, `AZURE_CLIENT_CERTIFICATE_PASSWORD` or `AZURE_PASSWORD`, the credentials the AWS SDK and the Azure identity library read from the backend's environment. EUDIPLO declares none of them as a setting, so the rule above does not cover them. The global `kms.json` still resolves them, and a tenant `kms.json` if `KMS_TENANT_VARIABLES` lists them.
- `PUT /api/key-chain/providers/config` and the import of a configuration bundle answer `400` (plan issue `KMS_PLACEHOLDER_REFUSED`) for a value that contains a placeholder, unless the stored tenant file holds the same value in the same field of the provider, the address the provider's credentials are sent to stays the same, and the variable is listed and set. This includes `eudiplo config plan` and `eudiplo config import` for a folder whose `kms.json` keeps placeholders that `--allow-env` does not fill in.

A file that names a variable it may not use is rejected: a tenant `kms.json` is not loaded, so the tenant's key operations answer `400` and the backend logs the file with the variable's name at startup; like every other tenant folder file, it also fails the startup import of that tenant and a reattach of the resource in that file; the same holds for a tenant `kms.json` that contains `${VAR:default}`, a form `kms.json` never resolved, with every value of `CONFIG_VARIABLE_STRICT`; a global `kms.json` stops the startup. Earlier releases resolved every variable of the backend's environment in every file. Because a tenant's administrators (`tenant:admin`) write the tenant `kms.json` through the API, they could make the backend send any variable of the instance, such as `MASTER_SECRET`, as the credential of a Vault or HTTP provider at an address of their choice, or read it in the API response by naming it in the `id` of a provider.

**Do:** before you upgrade, search the tenant `kms.json` files for `${`. For placeholders you wrote, add the variables to `KMS_TENANT_VARIABLES`; in `defaultProvider` and the `id` of a provider, replace the placeholder with exactly the value the variable has, because key chains refer to their provider by that ID; for a variable of EUDIPLO, set a variable of your own to the same value and name that one. Search the other files of the tenant folders for the AWS and Azure variables named above and replace them in the same way. If you did not write such a placeholder, treat these credentials of the instance as disclosed to the address in that file and rotate them. Treat a placeholder you did not write as a disclosure of that variable to the provider address in the file, and one in a provider `id` as a disclosure to everyone who could list the tenant's KMS providers (`GET /api/key-chain/providers`, its health endpoint or the KMS configuration): rotate the secret, and remove or replace the file; what a change of `MASTER_SECRET` involves is described in [Keep the key stable](../operate/encryption-keys.md#keep-the-key-stable). In clients that send placeholders to the API, send the values instead. Details: [Placeholders in a tenant `kms.json`](../operate/kms.md#placeholders-in-a-tenant-kmsjson).

### Exports: placeholder text is written in an escaped form

**Changed:** a value stored through the API that contains `${` is text, and configuration files now have a way to say so ([placeholders and the API](../reference/config-bundle-format.md#placeholders-and-the-api)):

- In a configuration file, `$${` stands for the two characters `${` and starts no placeholder. Earlier releases read `$${VAR}` in a tenant folder file as a `$` followed by the placeholder `${VAR}`. A `kms.json` is read as before.
- Exports (`GET /api/config-bundles/export`, the document of a single resource and `eudiplo config export`) write every `${` of a stored value as `$${`. The placeholders an export writes for secrets are unchanged.
- `GET /api/key-chain/{id}/export` and `GET /api/trust-list/{id}/export` write every `${` of a stored value as `$${` too, since their responses are configuration files, which can end up in a tenant folder. A create request stores such a response as sent, so a value that contained `${` comes back as `$${` after a round trip through `POST /api/key-chain/import` or `POST /api/trust-list`; send the export as a document in a bundle to keep the text.
- A configuration bundle sent to the API, also with `eudiplo config plan` and `eudiplo config import`, stores `$${` as the text `${`; earlier releases stored `$${` as sent. A `${VAR}` inside a longer value is still stored as text, now with the plan warning `PLACEHOLDER_STORED_AS_TEXT`; a value that is a placeholder and nothing else blocks the resource with `SECRET_REQUIRED`, as before.

Requests that create or update a resource are unchanged and store the value as sent. Earlier releases exported such a value as it is. An operator who placed that export in the tenant's folder in `CONFIG_FOLDER` thereby made the backend resolve the placeholder from its own environment at the next start or reattach, so a tenant could read a variable of the instance, such as a secret meant for another tenant's files, in the resource or have it sent to a webhook address of its choice.

**Do:** search the tenant folders in `CONFIG_FOLDER` for `${`. A placeholder you did not write came from an export of an earlier release: write it as `$${`, and if the backend has started or the resource was reattached since the file was placed, treat the named variable as disclosed to that tenant and rotate it. Export tenants again with this release before you place them in a folder; an export made by an earlier release stays unescaped. If a file of yours contains `$${` and means a `$` before a placeholder, set a variable of your own to the whole value and name that one. In bundles you send to the API, check values that contain `$${`: they are now stored as `${`, also in an export of an earlier release whose stored text happened to contain `$${`. Upgrade the CLI together with the backend: a CLI of this release sends `$${` and escapes the values it fills in from `--allow-env`, which an earlier backend stores as they are, and an earlier CLI sends such values unescaped. Import an export of this release only into this release or a later one: an earlier release does not know the escaped form, stores `$${` as it is when the bundle is sent to its API, and resolves the placeholder behind it in a tenant folder.

### Tenant KMS configuration: host files and the instance's AWS identity need the operator

**Changed:** a tenant `kms.json` (`<CONFIG_FOLDER>/<tenant-id>/kms.json`) is limited in what it can make the backend use of its own host and cloud account ([files and AWS credentials in a tenant `kms.json`](../operate/kms.md#files-and-aws-credentials-in-a-tenant-kmsjson)):

- It can name a file of the backend's host, the `library` of a `pkcs11` provider or the mTLS `certFile`, `keyFile` and `caFile` of an `http` provider, only if the new setting `KMS_TENANT_FILES` (comma-separated absolute paths, empty by default) lists it.
- Its `aws-kms` providers need `accessKeyId` and `secretAccessKey`. The AWS SDK default credential chain (IAM role, IRSA, `AWS_*` variables) is available to the global `kms.json`, and to tenant files only with the new setting `KMS_TENANT_AWS_DEFAULT_CREDENTIALS=true` (off by default).
- `PUT /api/key-chain/providers/config` and the import of a configuration bundle answer `400` (plan issue `KMS_SETTING_REFUSED`) for a `library` or mTLS file, also a listed one, unless the stored tenant file holds the same path in the same setting of the provider, the file is still listed and, for an `http` provider, `baseUrl` stays the same. They answer `400` for an `aws-kms` provider without credentials, also with `KMS_TENANT_AWS_DEFAULT_CREDENTIALS`, unless the setting is on and the stored tenant file holds that provider without credentials and with the same `region`.
- The servers of its providers (`vaultUrl`; `baseUrl` and `auth.tokenUrl` of an `http` provider; `baseUrl` and `tokenUrl` of a `csc` provider) must pass the [outbound URL policy](../concepts/security-model.md#https-and-tls): HTTPS, a public address and, when `OUTBOUND_URL_ALLOWED_HOSTS` is set, a listed host ([servers in a tenant `kms.json`](../operate/kms.md#servers-in-a-tenant-kmsjson)). `PUT /api/key-chain/providers/config` and the import of a configuration bundle answer `400` (`KMS_SETTING_REFUSED`) for another server. A host name that resolves to a private address is refused when the provider is used, and these providers no longer follow redirects; a request to them must finish within 30 seconds and its body and answer are limited to 1 MiB each, and it does not use the proxy in `HTTPS_PROXY`. The global `kms.json` is not concerned.
- An mTLS file is read only if it is a regular file of at most 1 MiB, also for the global `kms.json`.
- `keysPath` and `healthPath` of an `http` provider and `apiPath` of a `csc` provider must be paths on the server of `baseUrl`, also in the global `kms.json`. A value such as `@other.example/keys` made the backend send the provider's credentials, including a stored one sent back as `<redacted>`, to another server; it is now refused: the API answers `400`, a tenant `kms.json` is not loaded, and a global `kms.json` with such a path stops the startup.

A stored tenant `kms.json` that breaks the first two rules, or names a server the policy refuses, is not loaded: all key use of that tenant answers `400`, also for key chains of other providers such as `db`, so its issuance, presentation and status list signing stop until the file is corrected; an import of key chains from the tenant's folder fails, and so does `GET /api/key-chain/providers/config`. The backend logs the file at startup, unless the path or server is written as a `${VAR}` placeholder. Earlier releases accepted these settings from a tenant's administrators (`tenant:admin`), who write the tenant `kms.json` through the API. They could make the backend load a file as native code, including a file they had uploaded to local storage, stop the backend with a file such as `/dev/zero`, present a client certificate of the host to a server of their choice, call AWS KMS with the identity of the instance, and name a KMS service of the operator's network that does not authenticate the backend as a provider of their own, to use the keys of other tenants in it.

**Do:** before you upgrade, search the tenant `kms.json` files for `"pkcs11"`, `"mtls"` and `"aws-kms"`, and for servers on HTTP or inside your network. Move a provider with such a server to the global `kms.json`, where every tenant can use it as a shared provider, or set `OUTBOUND_URL_ALLOW_HTTP` and `OUTBOUND_URL_ALLOW_PRIVATE_NETWORK`, which apply to every outbound URL of the instance; if `OUTBOUND_URL_ALLOWED_HOSTS` is set, add the hosts of tenant KMS servers to it. Check a server written as a `${VAR}` placeholder by the variable's value: the startup log does not report it, and the tenant's key use fails when it first needs a key. Name the final address of each server: one that answers with a redirect, such as a Vault standby node or a load balancer that redirects to the active node, now fails. For providers you wrote, add their files to `KMS_TENANT_FILES`, and give `aws-kms` providers credentials, move them to the global `kms.json`, or set `KMS_TENANT_AWS_DEFAULT_CREDENTIALS=true`. Treat such a provider you did not write as an incident: check which file the `library` names and whether it is one of yours, remove the provider, and for `aws-kms` review the KMS activity of the instance's AWS identity (CloudTrail). In clients that send these settings to the API, write the provider to the tenant's file instead.

### Key chains: keys of a shared KMS provider stay with their tenant

**Changed:** for integrators, CLI users and operators: on a KMS provider that several tenants use with the same credentials, a request can no longer make a key chain point at a key of the tenant's choice ([keys of a provider that tenants share](../operate/kms.md#keys-of-a-provider-that-tenants-share)). Shared are the providers of the global `kms.json`, and providers of a tenant `kms.json` that use the instance's AWS identity, mTLS files or a `${VAR}` placeholder.

- `POST /api/config-bundles/import` answers `400` (plan issue `KMS_REFERENCE_REFUSED`) for a `KeyChain` document whose `external-reference` key source names a key on a shared provider that no key chain of the tenant holds on that provider. This includes `eudiplo config import`. Importing an export again into the tenant that holds the keys works as before, unless the key chain was rotated since the export: the export then names a key the tenant no longer holds. A key chain file in the tenant's configuration folder also works as before, at startup and on reattach.
- `PUT` and `DELETE /api/key-chain/providers/config` answer `409`, and a bundle plan is blocked with `KMS_PROVIDER_IN_USE`, when they would remove a provider that holds its own credentials from the tenant's `kms.json`, or change it into a shared one, while key chains of the tenant use it. A shared provider with the same `id`, now or later, would otherwise take its place. `db` providers are not concerned.
- A private key that a request imports into a shared provider (`POST /api/key-chain/import`, or a `KeyChain` document with a `private-jwk` key source sent to the API) is stored under a name EUDIPLO chooses, `<key chain id>-import-<random>`. The `kid` of the imported JWK is no longer the key's name in the provider, and a standalone key chain publishes the new name as its `kid`. This applies to Vault and HTTP providers that accept imports. Key chain files of a configuration folder keep their key names.
- `POST /api/key-chain/import` without an `id` now takes the tenant's configuration lock, as it already did with an `id`: while another configuration change of the tenant runs, on any replica, or an interrupted one waits for recovery, it answers `409` with `CONFIG_WRITER_ACTIVE` ([locks](../operate/configuration-as-code.md#plans-locks-and-recovery)).
- A tenant `kms.json` is read again whenever the file changed, also when another backend replica wrote it. A file you edit by hand therefore applies at the tenant's next key operation, not at the next restart. Before, a replica kept the providers it had loaded until it restarted, so after a tenant added its own provider through one replica, the other replicas kept using the global provider of the same `id` for that tenant. When the file changes, `pkcs11`, `aws-kms` and `http` providers with mTLS are connected anew: a key operation that still runs on the earlier connection after one minute fails and can be retried.

Earlier releases accepted these requests and used the caller's key name. A tenant's administrators (`tenant:admin`) who knew the name or ID of another tenant's key in a shared provider, which Vault, HTTP and PKCS#11 providers publish as the `kid` of the key, and its public key could import a key chain that refers to it, or create a key of that name in a provider of their own and then remove that provider. They could then sign with the other tenant's key and, by deleting their key chain, delete it. With an HTTP provider whose service overwrites a key on import, they could also replace the other tenant's key.

**Do:** if tenants you do not trust with each other's keys share a KMS provider, compare each tenant's key chains with the keys you expect it to have, and review the KMS's own audit log for signatures and deletions. To attach a key that a tenant does not hold yet, put the key chain file into `<CONFIG_FOLDER>/<tenant-id>/key-chains/`. Send the key imports of one tenant one after the other and retry on `409` with `CONFIG_WRITER_ACTIVE`; if it persists, an operation was interrupted: stop its process and release the lock with `eudiplo config recover` ([locks](../operate/configuration-as-code.md#plans-locks-and-recovery)). With several backend replicas, check that all of them mount the same `CONFIG_FOLDER` volume. Before you remove a tenant's own provider, delete the key chains that use it. If you look up imported keys in a shared Vault or HTTP KMS by the `kid` you imported them with, use the `kid` the key chain shows instead.

### Status lists: capacity is limited to 1,000,000 on every path

**Changed:** no new status list is built with more than 1,000,000 statuses, and no tenant default above 1,000,000 is stored:

- `PUT /api/status-list-config`, `POST /api/tenant` and `PATCH /api/tenant/{id}` answer `400` for a status list `capacity` above 1,000,000 (`Status list capacity must be an integer between 1 and 1000000`).
- In a configuration bundle (`POST /api/config-bundles/import` and `/import/archive`, also with `eudiplo config import`) or a configuration folder, a `StatusList` document that would create a new list with such a `capacity` is a plan error (`STATUS_LIST_CAPACITY_OUT_OF_RANGE`), and so is a `Tenant` document whose `statusListConfig.capacity` is above 1,000,000 (`CURRENT_SCHEMA_VALIDATION_FAILED`): the import answers `400` `CONFIG_APPLY_BLOCKED` and applies nothing, `eudiplo config plan` exits with `1`, and a startup import skips the tenant and logs the issue.
- A new list without `capacity` takes the tenant default. If a default above 1,000,000 is already stored, `POST /api/status-lists` and issuance refuse to create the list as before, a bundle import now stops at that `StatusList` document with `500` `CONFIG_APPLY_FAILED` (the documents applied before it stay applied), and a startup import logs `CONFIG_APPLY_FAILED` for the tenant.

Status lists that already exist are not changed, also those above 1,000,000 statuses, and their documents and exports still import. The published configuration schemas are unchanged. Earlier 10.x releases applied the limit only to `POST /api/status-lists` and to lists created during issuance: an import with a large `capacity` built and shuffled the whole list in memory first, so a tenant administrator could stall the backend or exhaust its memory for every tenant.

**Do:** if a configuration file or bundle would create a new status list with a `capacity` above 1,000,000, lower it, or split the list. Check the tenant defaults with `GET /api/status-list-config`: set one above 1,000,000 to 1,000,000 or less, or reset it with `DELETE /api/status-list-config`. Details: [Manage status lists](../issuance/revocation.md#manage-status-lists).

### Access tokens of an OIDC provider: the key set is fetched at most every 30 seconds

**Changed:** with `OIDC_PROVIDER=keycloak` or `generic`, EUDIPLO fetches the provider's key set at most once every 30 seconds, and every 10 minutes while tokens arrive. A token whose `kid` is not in the key set fetched last gets `401` without a fetch when the last fetch is less than 30 seconds old. A token with a known `kid` is checked against the keys fetched last, also when a fetch fails, for up to one hour after the last successful fetch; after that, tokens get `401` until the key set can be read again (earlier releases: 10 minutes). Earlier 10.x releases fetched the key set for every unknown `kid`, up to 5 times a minute, and once that limit was used up refused every token whose key had not been fetched in the last 10 minutes: anyone could send tokens with random `kid` values to make valid tokens fail with `401`, in particular right after the provider rotated its keys.

**Do:** nothing. After your provider adds a signing key, tokens signed with it can get `401` for up to 30 seconds; retry them. Details: [Other OIDC providers](../operate/oidc-provider.md).

### Clients: with Keycloak, only clients EUDIPLO manages for a tenant have their secret rotated

**Changed:** with `OIDC_PROVIDER=keycloak`, `POST /api/client/<id>/rotate-secret` rotates only a client that EUDIPLO created or took over for a tenant. It answers `404` for every other client of the realm: clients of other applications, a client created directly in Keycloak that EUDIPLO has no record of, EUDIPLO's admin-API client (`OIDC_CLIENT_ID`) and its bootstrap client (`AUTH_CLIENT_ID`). This applies to callers with `tenants:manage` too. When the client's `tenant_id` attribute in Keycloak names another tenant than EUDIPLO's record, the call answers `409`. Earlier 10.x releases looked the client up in the whole realm when the caller had `tenants:manage`, and returned a new secret for any of them: such a caller could take over the admin-API client, and with it the Keycloak admin API, or a client of another application, and locked EUDIPLO out of the admin API at its next login. The built-in server is unchanged.

**Do:** to change the secret of `OIDC_CLIENT_ID`, regenerate it in Keycloak and set `OIDC_CLIENT_SECRET`; for `AUTH_CLIENT_ID`, change `AUTH_CLIENT_SECRET`; restart EUDIPLO in both cases. To rotate a tenant's client that was created directly in Keycloak, set its Keycloak attribute `tenant_id` to the tenant's ID and take it over with `POST /api/client` and its ID ([taking over a Keycloak client](../operate/keycloak.md#4-give-people-access)). If you rotated `OIDC_CLIENT_ID` through the API on an earlier release, check that `OIDC_CLIENT_SECRET` matches the secret in Keycloak. Details: [Granting roles](../reference/roles.md#granting-roles).

### Issuance: every mDOC claim path names a namespace

**Changed:** in an `mso_mdoc` credential configuration, a top-level field without `namespace` and with a one-segment `path`, such as `["given_name"]`, and its children without a `namespace` of their own, belong to the document type's namespace (`org.iso.18013.5.1` for `org.iso.18013.5.1.mDL`, the document type otherwise):

- The issuer metadata publishes their claim paths with that namespace in front, for example `["org.iso.18013.5.1", "given_name"]`. Earlier 10.x releases published `["given_name"]`, which OID4VCI 1.0 Appendix C.2 does not allow: a claims path pointer for an mDOC starts with the namespace, and a wallet aborts on one with fewer than two components.
- Default values of such fields, and of their children, are issued in that namespace. Earlier 10.x releases issued a child's default value in a namespace named after its parent (`address` for the child `street` of `["address"]`) and then left the parent's claims from the session out of the default namespace. Values from the session were already issued in the default namespace.

Fields with `namespace`, their children and fields with a nested `path` (whose first segment names the namespace) are unchanged. A one-segment parent named like a namespace, such as `["eu.europa.ec.eudi.pid.1"]` in an mDL, is now an element of the default namespace, and so are its children.

**Do:** nothing, unless something compares published mDOC claim paths with the old one-segment form, such as a DCQL query or test fixture built from the metadata; set `namespace` on the fields to make the namespace explicit. Details: [Credential configuration](../reference/credential-configuration.md).

## Wallet-facing behavior

### Presentations: a credential of another type is refused

**Changed:** a wallet that answers a credential query with a credential of a type its `meta` does not name gets HTTP 400: in OpenID4VP flows the `Incomplete Presentation` error body described in [What the wallet or browser receives](../reference/session-outcome.md#what-the-wallet-or-browser-receives), in ISO 18013-7 flows `{"error": "credential_type_mismatch", "message": "..."}`. With a configured redirect, the redirect carries `error=invalid_request` and the message as `error_description`.

This includes an SD-JWT VC whose `vct` only extends a listed one, which OpenID4VP 1.0 Appendix B.3.5 lets a wallet return: EUDIPLO does not follow type inheritance.

**Do:** wallets that present only credentials whose `vct` or docType the query lists need no change.

### Presentations: an mDOC whose CBOR repeats a map key is refused

**Changed:** a wallet that presents an mDOC in which a CBOR map repeats a key gets HTTP 400, as for any other mDOC that does not verify ([What the wallet or browser receives](../reference/session-outcome.md#what-the-wallet-or-browser-receives)). Earlier 10.x releases read the last entry and went on.

**Do:** wallets and issuers that encode each map key once need no change.
