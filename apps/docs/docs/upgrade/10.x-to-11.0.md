# Upgrading from 10.x to 11.0

This guide lists the changes in EUDIPLO 11.0 that can need action. It grows until 11.0 is released.

## Before you upgrade

1. Upgrade from any 10.x release. On 9.x or older, [upgrade to 10.x first](./index.md#upgrade-guides).
2. Take the backups of the [upgrade procedure](./index.md#upgrade-procedure).

Then check every row that applies to your setup:

| If you … | Check |
| --- | --- |
| create configurations through the API, the SDK or scripts | A `POST` that names an ID the tenant already uses answers `409` and no longer replaces the stored configuration. Change a stored configuration with its `PATCH` or `PUT` request ([Creates refuse a taken ID](#integrators-creates-refuse-a-taken-id)). |
| use registration certificates in presentation configurations | A registration certificate whose `sub` (or, with an intermediary, `intermediary.sub`) is not the `organizationIdentifier` (legal person) or `serialNumber` (natural person) of the signing access certificate is refused when saved and fails every request with `400` ([Registration certificate must match the access certificate](#integrators-operators-and-wallets-registration-certificate-must-match-the-access-certificate)). |

## Integrators: creates refuse a taken ID

Up to 10.x, these requests replaced a stored resource with the same `id` without a warning:

| Request | Change the stored resource with |
| --- | --- |
| `POST /api/issuer/credentials` | `PATCH /api/issuer/credentials/{id}` |
| `POST /api/verifier/config` | `PATCH /api/verifier/config/{id}` |
| `POST /api/issuer/webhook-endpoints` | `PATCH /api/issuer/webhook-endpoints/{id}` |
| `POST /api/issuer/attribute-providers` | `PATCH /api/issuer/attribute-providers/{id}` |
| `POST /api/trust-list` (with an `id` in the body) | `PUT /api/trust-list/{id}` |

From 11.0 they answer `409 Conflict` and leave the stored resource as it is. The `message` of the response names the resource and the ID, for example `Credential configuration 'pid' already exists. Choose another ID, or update the existing one.` The Web Client reports the taken ID when you save a new resource under it; the verification config form also marks its ID field.

`POST /api/federation-trust-anchor` already answered `409` for a taken ID; it is unchanged.

**What to do:** in scripts that send the same configuration again to bring it up to date, send it with the update request from the table, or delete the stored resource first. To keep configurations in files and apply them repeatedly, use the configuration folder or a configuration bundle (`eudiplo config import`) instead: both still replace stored resources as before ([Configuration as code](../operate/configuration-as-code.md)).

A `PATCH` takes the fields it changes; set an optional field to `null` to clear it. A `PUT /api/trust-list/{id}` takes the whole list, as `POST` does.

## Integrators, operators and wallets: registration certificate must match the access certificate

Up to 10.x, EUDIPLO attached a presentation configuration's `registration_cert.jwt` whichever access key chain signed the request. Wallets refuse a registration certificate of another relying party than the access certificate's (ETSI TS 119 475, clause 5.1).

From 11.0, the `sub` of the registration certificate (`intermediary.sub` when the relying party acts through an intermediary; `sub.id` and `act.sub.id` in certificates of ETSI TS 119 475 v1.1.1) must equal the `organizationIdentifier` (legal person) or `serialNumber` (natural person) in the subject of the access certificate: the leaf of the configuration's `accessKeyChainId`, or of the tenant's default access key chain. Otherwise:

- creating a presentation configuration, or an update that changes `registration_cert`, `dcql_query` or `accessKeyChainId`, answers `400` with "The registration certificate does not belong to the access certificate" and both identifiers;
- an update that changes only `accessKeyChainId` now checks the stored certificate in full, so an expired one or one that no longer covers the DCQL query is refused too;
- a configuration bundle plan (`eudiplo config plan`) or config folder blocks the presentation config with `REGISTRATION_CERTIFICATE_REFUSED`, and a config folder with such a file imports none of that tenant's files at startup until the file is fixed. When the bundle or folder also contains a `KeyChainDefaults` document or an access `KeyChain` document, as full exports usually do, the plan cannot tell which access certificate applies and does not report the mismatch; the import then stops at that presentation config with `CONFIG_APPLY_FAILED`, the documents before it stay applied and later ones are not applied (for a config folder, on every start until the file is fixed). Compare the identifiers yourself before you roll out 11.0;
- requesting a verifier registration certificate from the EUDI Hub for a presentation configuration whose access key chain is not one of the Hub organization's, including an access key chain EUDIPLO generated, answers `400`, and the certificate the Hub just issued is revoked again;
- every presentation request of a stored configuration that does not match answers `400`, including the request object of a session created before the upgrade. Requests with an `openid_federation` client ID are not matched. A wallet fetching such a request gets the `400` instead of a request object. Saving does not check stored configurations again when you later change the tenant's default access key chain or renew an access certificate with another subject; their requests then start failing, so check them after such a change.

A registration certificate without an identifier in `sub` and without an intermediary is not matched. One that names an intermediary without its identifier (`intermediary` without `intermediary.sub`, or `act` without `act.sub`) is refused. Details: [Access certificate match](../trust/registration-certificates.md#access-certificate-match).

**What to do:** before upgrading, compare the `sub` (or `intermediary.sub`) of each stored registration certificate with the subject of the access key chain it is sent with. Where they differ, request a registration certificate for the relying party of that access certificate, or select the access key chain the certificate was issued for. An access certificate generated by EUDIPLO itself carries no `organizationIdentifier`, so a registrar-issued registration certificate with `sub.id` no longer works with it.
