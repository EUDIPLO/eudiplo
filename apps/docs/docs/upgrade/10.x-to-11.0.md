# Upgrading from 10.x to 11.0

This guide lists the changes in EUDIPLO 11.0 that can need action. It grows until 11.0 is released.

## Before you upgrade

1. Upgrade from any 10.x release. On 9.x or older, [upgrade to 10.x first](./index.md#upgrade-guides).
2. Take the backups of the [upgrade procedure](./index.md#upgrade-procedure).

Then check every row that applies to your setup:

| If you … | Check |
| --- | --- |
| give API clients or people roles: built-in server, Keycloak, another OIDC provider or configuration files | Roles now include other roles, three roles are new, and `clients:manage`, `issuance:manage`, `presentation:manage` and `tenant:admin` changed. EUDIPLO adds roles so clients keep their access; check the accounts it cannot change ([Role model](#operators-role-model)). |
| create configurations through the API, the SDK or scripts | A `POST` that names an ID the tenant already uses answers `409` and no longer replaces the stored configuration. Change a stored configuration with its `PATCH` or `PUT` request ([Creates refuse a taken ID](#integrators-creates-refuse-a-taken-id)). |

## Integrators: creates refuse a taken ID

Up to 10.x, these requests replaced a stored resource with the same `id` without a warning:

| Request | Change the stored resource with |
| --- | --- |
| `POST /api/issuer/credentials` | `PATCH /api/issuer/credentials/{id}` |
| `POST /api/verifier/config` | `PATCH /api/verifier/config/{id}` |
| `POST /api/issuer/webhook-endpoints` | `PATCH /api/issuer/webhook-endpoints/{id}` |
| `POST /api/issuer/attribute-providers` | `PATCH /api/issuer/attribute-providers/{id}` |
| `POST /api/trust-list` (with an `id` in the body) | `PUT /api/trust-list/{id}` |

From 11.0 they answer `409 Conflict` and leave the stored resource as it is, also when two creates of the same new ID arrive at the same time: one is stored, the other answers `409`. The `message` of the response names the resource and the ID, for example `Credential configuration 'pid' already exists. Choose another ID, or update the existing one.` The Web Client reports the taken ID when you save a new resource under it; the verification config form also marks its ID field.

`POST /api/federation-trust-anchor` already answered `409` for a taken ID. Its `message` now ends with the same hint: `Federation trust anchor '<id>' already exists. Choose another ID, or update the existing one.`

**What to do:** in scripts that send the same configuration again to bring it up to date, send it with the update request from the table, or delete the stored resource first. To keep configurations in files and apply them repeatedly, use the configuration folder or a configuration bundle (`eudiplo config import`) instead: both still replace stored resources as before ([Configuration as code](../operate/configuration-as-code.md)).

A `PATCH` takes the fields it changes; set an optional field to `null` to clear it. A `PUT /api/trust-list/{id}` takes the whole list, as `POST` does.

## Integrators: role model

Scripts and integrations that call the management API or the SDK notice three changes of the [role model](#operators-role-model):

- A client with `issuance:manage` or `presentation:manage` that creates, imports, rotates or deletes key chains, requests a CSR or sets the default access key chain needs `keys:manage`; the upgrade adds it to existing clients.
- A client that reads the audit log (`/api/admin/audit-logs`) with `clients:manage` needs `audit:read`; the upgrade adds it to existing clients.
- `GET /api/auth/me` returns the roles with those they include, for example `issuance:read` for a client with `issuance:offer`. Code that compares the list with the assigned roles needs to allow for them.

New roles appear in the role enums of the SDK and the API: `issuance:read`, `presentation:read` and `keys:export`.

## Configuration files: Client v3

Client files and bundle documents use format v3, which accepts the new roles. Importing a v2 file adds `audit:read` and `keys:manage` where the [role model](#operators-role-model) needs them and reports each with the warning `CLIENT_ROLES_ADDED`; `eudiplo config upgrade` writes the upgraded files. A `!generate` client that a source applied before keeps its secret. Files that 11.0 exports cannot be imported into 10.x.

## Operators: role model

11.0 makes roles include narrower ones, adds read roles and moves key chain writes and key export to their own roles. The [roles reference](../reference/roles.md#how-roles-include-each-other) lists the whole model.

**Roles include other roles:** for example `issuance:manage` includes `issuance:offer`, which includes `issuance:read`, and `tenant:admin` includes every role except `tenants:manage`. The [roles reference](../reference/roles.md#how-roles-include-each-other) lists all of them.

So a client with `issuance:manage` now also creates offers and sees issuance sessions, which needed `issuance:offer` before, and `tenant:admin` calls every endpoint of its tenant instead of only configuration bundles, key export and KMS settings. `GET /api/auth/me` returns the roles with those they include. A caller can grant the roles its roles include, so `tenant:admin` still grants every role except `tenants:manage` and `tenant:admin`.

**New roles:**

- `issuance:read` and `presentation:read` read the configurations of their side, trust lists, federation trust anchors, webhook endpoints, session settings and key chains, without changing them. `issuance:offer` can now read the credential and issuance configurations it offers, so **New Issuance** in the Web Client needs only `issuance:offer`.
- `keys:export` exports key chains with their private keys (`GET /api/key-chain/{id}/export` and the `KeyChain` configuration document) and manages the tenant's KMS provider settings (`/api/key-chain/providers/config`), which needed `tenant:admin` or `tenants:manage` before.

**Narrowed roles:**

- `clients:manage` no longer reads the audit log; that needs `audit:read`.
- `issuance:manage` and `presentation:manage` no longer create, import, change, rotate or delete key chains, request a CSR or set the default access key chain; that needs `keys:manage`. They still read key chains and select them in their configurations. Listing the ownership of `KeyChain` and `KeyChainDefaults` resources (`GET /api/config-bundles/resources/{kind}`), which the Web Client uses to lock file-managed key chains, and downloading the `KeyChainDefaults` document need `keys:manage` as well.

**What EUDIPLO changes on the upgrade:** so that nobody loses access, a client that has `clients:manage` gets `audit:read`, and one that has `issuance:manage` or `presentation:manage` gets `keys:manage`, unless it has `tenant:admin` or `tenants:manage`. This happens:

- with the built-in server, in a database migration on the first start;
- in configuration files: Client format v3 adds the roles to v2 files when they are imported, and `eudiplo config upgrade` writes them. A `!generate` client that a source applied before keeps its secret;
- with Keycloak, on the first start, for the users and service accounts that have the role mapped directly. The start logs composite realm roles that contain one of the narrowed roles. Roles from Keycloak groups and composite roles are not changed.

EUDIPLO creates the new realm roles in Keycloak on that start, as for every new role, and runs this upgrade only while `keys:export` is missing in the realm: it creates `keys:export` once the upgrade has finished. If the upgrade fails, for example because the service account of `OIDC_CLIENT_ID` may not view users, the start logs the error, goes on and tries again on the next start. Without `realm-admin`, that service account needs `view-users`, `manage-users` and `view-realm` of `realm-management` for the upgrade. Until the upgrade has run, the realm has no `keys:export` role, and granting it to a Keycloak user or client is skipped without an error; grant it again after a start that logged no upgrade error.

**What to do:**

1. With Keycloak, give groups and composite roles that contain `clients:manage` the role `audit:read`, and those with `issuance:manage` or `presentation:manage` the role `keys:manage`, where their members need them. The startup log names the composite roles.
2. With another OIDC provider (`OIDC_PROVIDER=generic`), EUDIPLO cannot change the roles: add the same roles in the provider before you upgrade.
3. After the upgrade, remove `audit:read` and `keys:manage` where an account does not need them, for example `keys:manage` from an application backend that only creates offers through `issuance:manage`. Give `issuance:read` or `presentation:read` to accounts that only look at configurations.
4. Give `keys:export` to accounts that export keys or change the KMS settings and have neither `tenant:admin` nor `tenants:manage`.

Configuration files and bundles exported by 11.0 name roles that 10.x does not know and use Client format v3, so they cannot be imported into 10.x.
