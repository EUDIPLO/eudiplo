# Upgrading from 10.x to 11.0

Each section below says what changed in EUDIPLO 11.0 and what to do; skip the sections that do not apply to you.

## Before you upgrade

- Upgrade from any 10.x release. On 9.x or older, [upgrade to 10.x first](./index.md#upgrade-guides).
- Check that `meta.vct_values` and `meta.doctype_value` of your presentation configurations name the exact `vct` and docType of the credentials you accept: credentials of another type are now rejected ([Presentations](#presentations-credentials-must-be-of-a-requested-type)).
- If you use the demo `pid` presentation configuration from 10.x or earlier, update its `vct_values` ([Presentations](#presentations-credentials-must-be-of-a-requested-type)).
- Follow the [upgrade procedure](./index.md#upgrade-procedure).

## Operators

### Presentations: credentials must be of a requested type

**Changed:** a presented SD-JWT VC whose `vct` is not one of the credential query's `meta.vct_values`, or an mDOC whose docType is not its `meta.doctype_value`, fails with `credential_type_mismatch`, HTTP 400 to the wallet and session `failed` ([OpenID4VP 1.0, Section 8.6](https://openid.net/specs/openid-4-verifiable-presentations-1_0.html#section-8.6)). This applies to OpenID4VP flows, also over the Digital Credentials API, and to ISO 18013-7 flows. The values are compared as exact strings; in OpenID4VP flows `<TENANT_URL>` is resolved first. An SD-JWT VC whose type only `extends` one of `vct_values` is rejected too, because EUDIPLO does not resolve type metadata. 10.x accepted a credential of any type once its signature, issuer and claims checked out, so a wallet could answer a PID query with another credential of a trusted issuer.

The demo configuration's `pid` presentation now requests `urn:eudi:pid:de:1`, the `vct` of the demo PID. It requested `<TENANT_URL>/credentials-metadata/vct/pid`, which no demo credential carries.

**Do:** check that `vct_values` and `doctype_value` of every presentation configuration list the exact types your issuers put in their credentials, including every type that extends one you accept, for example `["urn:eudi:pid:1", "urn:eudi:pid:de:1"]`. If presentations fail with `credential_type_mismatch`, compare the message, which names the accepted types, with the `vct` or docType of the credentials wallets hold. If you imported the demo configuration or created a project with `eudiplo init` before 11.0, your stored `pid` presentation configuration still requests `<TENANT_URL>/credentials-metadata/vct/pid` and rejects the demo PID: set its `vct_values` to `["urn:eudi:pid:de:1"]`, or import the 11.0 demo file again. Details: [Credential type](../presentation/dcql.md#credential-type).

## Wallet-facing behavior

### Presentations: a credential of another type is refused

**Changed:** a wallet that answers a credential query with a credential of a type its `meta` does not name gets HTTP 400: in OpenID4VP flows the `Incomplete Presentation` error body described in [What the wallet or browser receives](../reference/session-outcome.md#what-the-wallet-or-browser-receives), in ISO 18013-7 flows `{"error": "credential_type_mismatch", "message": "..."}`. With a configured redirect, the redirect carries `error=invalid_request` and the message as `error_description`.

This includes an SD-JWT VC whose `vct` only extends a listed one, which OpenID4VP 1.0 Appendix B.3.5 lets a wallet return: EUDIPLO does not follow type inheritance.

**Do:** wallets that present only credentials whose `vct` or docType the query lists need no change.
